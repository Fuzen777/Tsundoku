## Introduction

- Tsundoku is a Windows desktop app (Tauri 2: a React + TypeScript UI over a Rust core) that downloads videos with yt-dlp and keeps a history of everything it has downloaded, so it can warn before a duplicate.
- [PROJECT.md](./PROJECT.md) holds the original spec and its decisions, [TODO.md](./TODO.md) the features planned after v1.

## Rules

- All UI text lives in `tsundoku/src/strings.ts`, in English. Never write UI text in a component.
- The queue is called **Downloads** wherever the user sees it (the view, Remove from Downloads, In Downloads, notifications) since 0.2.9: History is every download ever made, Downloads those added and not cleared yet. The code keeps the queue's names (`QueueView`, `QueueItem`, `queue_items`, `strings.queue`).
- UI labels use Title Case: buttons, toggles, navigation, headings, dialog titles and buttons, placeholders, column headers and short names. Minor words (a, an, the, and, or, of, to, in, on, for, with, as, at, by, from) stay lowercase unless first or last, and hyphenated words take both capitals. Sentences (descriptions, messages, empty-state explanations, status texts) stay in sentence case. See [DESIGN](./DESIGN.md).
- `tsundoku-core` (`tsundoku/core`) has no Tauri dependency. Downloads, the history, the tools, presets and settings go there, with unit tests; the app crate (`tsundoku/src-tauri`) only exposes them as commands and events, and the UI only presents.
- Types the UI reads are Rust types in the core deriving `ts_rs::TS` with `#[ts(export)]`; `cargo test` writes them to `tsundoku/src/bindings`. Never hand-write a TypeScript type that mirrors a Rust one, and commit the regenerated files with the change.
- `tsundoku/src/api.ts` is the only place that calls `invoke` or another Tauri API.
- Before a visual change, read [DESIGN](./DESIGN.md). If something differs notably from it, tell the user.
- Never suppress, ignore or work around an ESLint, Clippy or TypeScript error or warning; fix the cause.
- Meta files (docs, scripts) go at the project root; `tsundoku/` holds code only.
- After implementing a feature, update [FEATURES](./FEATURES.md) and remove the item from [TODO](./TODO.md) if it is listed.
- A change the checks can't confirm on their own (how it looks or behaves in the real app, a real site's answer) gets an entry in [TESTING](./TESTING.md) in the same commit: its version, where in the app, what to do and what should happen, and whether it was tried in the real app. Entries leave once the user confirms them.
- A question only the user can answer (an approval, a choice between two behaviours, whether to start something) goes on the [Open Decisions](https://claude.ai/artifact/A8Ewo1fPXDbs7CP6hgzwFj) page rather than waiting in a thread: add a document to its `decisions` collection with the ArtifactData tool (`title`, `group`, `order`, `context`, `source`, `options` as `{id, label, detail}`, `recommended` or `defaultOption`, `status: "open"`, `addedAt`), and meanwhile build the recommended answer where it is easy to change later. The user's answers are in its `answers` collection (`choice`, `choiceLabel`, `text`); the thread that acts on one sets the decision's `status` to `"done"` with a one-line `resolution`.
- Every change bumps the patch version and gets an entry in [CHANGELOG](./CHANGELOG.md); a commit that bumps the version is tagged `vX.Y.Z`. A release bumps the minor or major version and folds in the patch entries since the previous release.

### Build Folders and Worktrees

- A build folder only grows: every version bump gives our crates (`tsundoku_core`, `tsundoku_lib`, `tsundoku`) new build hashes, one each for the build, the tests and Clippy, and Cargo never deletes the old ones (0.3 to 1 GB each in `debug\incremental`, plus their files in `debug\deps`). The shared `D:\Dev\tsundoku\target` reached 231 GB on 2026-11-12.
- `Check.cmd` therefore ends with `Prune-Build.ps1`: in the build folder (cargo metadata's `target_directory`), it deletes our crates' entries in `deps`, `incremental`, `.fingerprint` and `build` that are more than an hour older than that crate's newest, never a third-party crate's or the files at the top of `debug\`. A profile whose Cargo lock a build holds is left alone, and it holds the lock itself while deleting. Versions built within the same hour (a rebase) are all kept.
- `tsundoku_lib` is an rlib only: the `staticlib` and `cdylib` of Tauri's template are for iOS and Android, and cost a 1.3 GB `.lib` per build.
- A thread working in a worktree lets it build into its own `tsundoku\target` (no `.cargo\config.toml` in it) rather than making a new `D:\Dev\tsundoku\target-*` folder.
- Once its work is on main, the thread runs `Scripts\Remove-Worktree.ps1 <worktree>`. It refuses the main checkout, a worktree whose HEAD isn't in main and one with uncommitted changes. Otherwise it removes the links in it (only the links: `node_modules` is the checkout's), deletes its build folder when that's inside it or a `target-*` folder beside the checkout's that no other worktree builds into (never the checkout's own), then runs `git worktree remove` and `git worktree prune`.

## Technical Notes

- The main window starts hidden and transparent (`tauri.conf.json`). `src-tauri/src/lib.rs` applies Mica, which needs Windows 11, and records whether it worked. `main.tsx` reads that through the `app_info` command before the first render and sets `data-backdrop` on `<html>`: `mica` makes the page transparent, `solid` paints `--color-bg`. `App` shows the window after its first frame, and Rust shows it anyway after 3 seconds if the UI never does.
- **Theme** (Settings → Appearance: `settings.appearance`, `appearance_options` and `save_appearance_options` in `src-tauri/src/appearance.rs`): `Theme::Auto`, `Light` or `Dark`. `appearance::apply_theme` calls the window's `set_theme` (`None` for Auto) in `setup`, while the window is still hidden, and again when the choice is saved. On Windows that sets the title bar's dark mode, which Mica's tint follows, and tao's `ThemeChanged` then makes tauri-runtime-wry set WebView2's preferred color scheme. The UI doesn't rely on that: `main.tsx` reads the options (`appearance_options`) with `app_info` before the first render and `theme.ts` sets `data-theme` on `<html>`, from which `index.css` sets `color-scheme` (`light`, `dark`, or `light dark` for Auto), so every `light-dark()` token follows. Choosing a theme sets `data-theme` at once, and back if saving fails. The accent (`AppearanceSettings.accent`, `Accent`) is the UI's alone: `applyAppearance` sets `data-accent` on `<html>` beside `data-theme`, and `index.css`'s `[data-accent="…"]` blocks override the four accent tokens, on any element, so the picker's swatches show their own. Custom (`AppearanceSettings.custom_accent`, `#rrggbb`, checked by `AppearanceSettings::checked` when saved) is set as `--accent-custom` on `<html>` whatever the accent, and its block derives the four tokens with relative OKLCH colors; the swatch opens Windows' color picker through `pick_color` (`appearance.rs`, `ChooseColorW` on a blocking thread, owned by the window, its 16 custom colors kept while the app runs), since WebView2 opens nothing for a color input; in a browser, `pickColor` clicks a temporary color input instead.
- `single-instance` is the first plugin registered, as it requires: a second launch focuses the running window. `window-state` restores size, position and maximized state, never visibility.
- Every Tauri permission the UI uses is listed in `src-tauri/capabilities/default.json`; `core:window:allow-show` is there for the hidden start.
- The CSP in `tauri.conf.json` allows `https:` images, for video thumbnails, and the `thumbnail`, `picture` and `sitepicture` protocols. Pixiv's pictures go through `sitepicture` (`api.ts`'s `sitePictureUrl`, in every `<img>` that can show a site's picture; `history::serve_site_picture` and `core::site_pictures::fetch`, which asks only `i.pximg.net` and `s.pximg.net`, with Pixiv's Referer, since Pixiv answers 403 without it), and previews ask for Pixiv's smaller copies (`site_pictures::pixiv_preview`: `c/540x540_70/img-master/…_master1200.jpg`). Network requests (GitHub) come from Rust, never from the UI.

### Releases

- A release is a version tag pushed to GitHub: `.github/workflows/release.yml` checks that the tag matches `package.json` and `Cargo.toml`, runs `Scripts\Check.cmd`, checks the committed bindings are current, then `tauri-action` builds the installer, signs it and publishes a release with `latest.json` for the updater, and a last step sets `.github/release-notes.md` as the release's text (`tauri-action` only takes it as a string). Before the build, "Read this version's changes" takes the version's CHANGELOG section (from its `## <version>` heading to the next `## `) as `tauri-action`'s `releaseBody`, which becomes `latest.json`'s `notes`, the update's `body` in the updater and the banner's What's New; the step after replaces only the release page's text. A version without a section warns and leaves the notes empty. Running the workflow by hand builds without publishing or signing, and keeps the installer with the run: a way to test a build before tagging.
- Push the tag on its own, after the commit (`git push origin main`, then `git push origin vX.Y.Z`). The v0.1.0 tag, pushed in one go with the commit that first added the workflow, started no run.
- A run takes about 20 minutes without a cache and 10 with one.
- Releases aren't marked pre-release, even for 0.x: the updater reads `releases/latest/download/latest.json`, and GitHub's "latest" skips pre-releases.
- Signing: the private key and its password are the repository's `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` secrets; the user keeps the key file outside the repository. Only the public key is in `tauri.conf.json` (`plugins.updater.pubkey`). Losing the private key means installed copies can't update anymore: a new key needs a new install.
- `src-tauri/tauri.release.conf.json` turns on the updater's files (`createUpdaterArtifacts`) for the release build only, since making them needs the private key. `Scripts\Build.cmd` builds the installer without them.
- `requireSignedVersion` is on: the updater refuses a release whose signature names another version, so an older signed release can't be served as a newer one.
- The installer is NSIS, per-user (`installMode: currentUser`), into `%LocalAppData%\Tsundoku`. Updates install in passive mode: a progress bar, no questions.
- While the repository is private, the update check fails (GitHub won't serve its release files without signing in) and the app shows nothing; Settings → About shows the error.

### Portable Copies

- A release build whose exe has `.portable.txt` beside it (`data_folder::PORTABLE_MARKER`) is portable. `make_portable_if_marked` in `src-tauri/src/lib.rs` checks before Tauri starts and sets `app.appDirectoriesOverride` (Tauri 2.12) on the context's config to the `data` folder beside the exe, so every app folder follows: `app_local_data_dir` (the data folder, which `data_folder::resolve` takes for a release build), `app_config_dir` (window-state's file) and the WebView's `EBWebView`. Development builds ignore the marker.
- `data_folder::set_portable_folder` records the copy's folder for the core (`data_folder::portable_folder`): a download folder that isn't a full path is inside it (`settings::BESIDE_APP_DOWNLOADS`, "Downloads", chosen at setup), so it follows the copy to another drive. `AppInfo.portable` tells the UI.
- A portable copy doesn't check for updates (`useAppUpdate` is off): Tauri's updater only runs the NSIS installer, which would install Tsundoku instead of replacing the copy. Replacing the exe in place (a `windows-x86_64-portable` entry in `latest.json`, signed with `version:` in its trusted comment since `requireSignedVersion` is on) and a zip in the release run are for a public portable release, with registering the notification ID (`HKCU\Software\Classes\AppUserModelId\<identifier>`, which the installer's shortcut does otherwise) and re-pointing Start with Windows when the folder moves (`enable()` also re-approves the entry in Task Manager, so only when the path changed).
- `background::startup_name` makes Start with Windows "Tsundoku (Portable)", apart from an installed copy's "Tsundoku". Both copies share the single-instance lock (the identifier), so only one runs at a time, and the browser bookmark's `tsundoku://` follows whichever started last.

### First-Run Choices

- `first_run::options` and `save` (the `first_run_options` and `save_first_run_choices` commands): where the tools go (`ToolsSettings.folder`, `None` for the data folder's `tools\`), their caches (`ToolsSettings.caches`) and the download folder. They're `needed` while `tools.caches` is `None` and yt-dlp or ffmpeg isn't set up, so an install from before 0.1.20 is never asked. The UI's `SetupView` shows `ChoicesScreen` first, then `ToolsScreen`; saving sets `needed` to false in the query, and Back sets it to true.
- `ToolManager::tools_folder` is the chosen folder or the data folder's `tools\`, for installs, updates, finding Tsundoku's copies and running them.
- A portable copy is also offered an installed copy's `tools\` in AppData (`FirstRunOptions.installed_tools_folder`: Tauri's `local_data_dir`, which the override leaves alone, joined to the identifier), picked when `tools::has_own_copies` finds Tsundoku's copies there. The tools screen's detection then finds them as Tsundoku's own (`locate::candidates` looks in the tools folder first), and Use This Copy sets them up as managed with no stored checksum.
- `ToolCaches::DataFolder` gives runs a `ToolCacheFolder` (`ToolManager::cache_folder`) for the data folder's `cache\`: yt-dlp gets `--cache-dir cache\yt-dlp` and its Deno `DENO_DIR=cache\deno` (`ProgramCommand::variable`, inherited by the Deno yt-dlp starts), gallery-dl `-o cache.file=cache\gallery-dl\cache.sqlite3`, whose folder Tsundoku makes since gallery-dl silently keeps its cache in memory otherwise. `UsualFolders` or `None` passes nothing. Previews (`FetchTools`, `GalleryTools`) and downloads (`JobSpec`) both get it.

### Backups

- Settings → About's Back Up and Restore (`views/settings/BackupRow.tsx`) call `save_backup` and `restore_backup` (`src-tauri/src/backup.rs`), which run `core::backup::create` and `restore`. A backup is a zip: `manifest.json` (`format`, `appVersion`, `schemaVersion`, `createdAt`), `settings.json` without `tools`, `tsundoku.db` and `archive.txt`.
- The database is copied with `VACUUM INTO` on the open connection, so the copy is consistent while downloads run; the copy then loses `queue_items` and `pending_links` and is switched to `journal_mode=DELETE`, so it's one file. The app crate manages the `Arc<Database>` for this.
- A restore reads and checks everything before changing anything, in a working folder under the data folder's `backups\`: a `format` or `appVersion` newer than this one, or a database `Database::open` refuses, is `NewerVersion`; opening the database also migrates an older one. It then saves the current data there as "Tsundoku Backup <local date and time> (Before Restore).zip", replaces the settings (keeping this PC's `tools` and `background.startWithWindows`, whose Windows entry is only changed when saved, and dropping a download folder that isn't a full path unless the copy is portable), then the history's rows and the past passwords (`past_passwords`) in one transaction through `ATTACH` (`SELECT *` works because both databases went through the same migrations), putting the settings back if that fails. Finished queue items are deleted, since their `result.downloadId` names a download in the replaced history. The UI restarts the app (`relaunch`) afterwards, so the shortcut, the tray, the theme and every query read what was restored.

### Passwords

- A link that needs a password Tsundoku can enter fails a read with `PreviewError::PasswordNeeded { wrong, tried }` (`wrong` when the password the person typed didn't open it, `tried` how many Tsundoku tried by itself first, see Tried Before Asking below); one it can't enter yet stays `PasswordProtected { site }`, whose message says so for that site. The UI asks with `components/PasswordForm.tsx` (a password field and Unlock, Enter submitting), on the preview card (`usePreview`'s `unlock`, keeping the field while it's tried, `tries` remounting it empty after a wrong one), on a pending link's row and under a queue row's Enter Password.
- `passwords::Password` holds it: its `Debug` prints `<password>`, it has no `Display` or `Serialize`, and `reveal` gives it to the request or tool that needs it. It's passed beside the link, never inside it: `hosts::read(link, password, …)`, `Host::read`, `FetchTools.password` (yt-dlp's `--video-password`, also in `runner::arguments`), `LinkReader::read`, `JobSpec.password`. The tauri commands take it as text (`fetch_preview`, `add_to_queue`, `add_post_to_queue`, `unlock_pending_link`, `enter_download_password`) and wrap it at once.
- **Where it's kept** (migration 15): `pending_links.password`, `queue_items.password` (`QueueItem.password`, `#[serde(skip)]` and `#[ts(skip)]`, so the UI never gets it) and `videos.password` (`History::record_opened_with`, `coalesce` keeping the last one). A new download looks the history up by site and ID (`DownloadQueue::password_for`), the preview card and a pending link's read by the exact link (`History::password_for_link`), so Download Again and Retry never ask. A backup copies `videos` whole, password included.
- **A host takes passwords** through `HostFacts::unlock`: a reader given the password typed (`Host::takes_passwords`). `Host::read` calls it when a password is given, else the host's `read`, and turns the host's `PasswordProtected` into `PasswordNeeded` (`wrong` when one was given) only for a host with `unlock`. A file whose address needs the password too carries it in its `FileSource`, in memory only. **None is switched on yet**: a host gets `unlock` only once a real link that needs a password downloaded through it (Fuzen's rule). MEGA's `#P!` decoding (MEGA's SDK `MegaClient::decryptlink`: algorithm 1 or 2, kind, handle, a 32-byte salt, the key XOR-ed with PBKDF2-HMAC-SHA512 of the password, 100,000 rounds, 64 bytes, and an HMAC-SHA256 keyed with the derived key's end, its key and message swapped for algorithm 1) is written and tested against links made by a separate script and three public links with their published passwords, all expired since (MEGA error -8, or -9); it waits in `D:\Dev\tsundoku\scripts\passwords\mega-unlock.patch` for a live link. How MediaFire (the file page's `downloadp` form), 1fichier (the file page's `pass` form), pCloud (`linkpassword` on `showpublink` and `getpublinkdownload`), Box (a form POST of `password` to the shared page, then its cookies) and TransferNow (`password` on `downloads/link`) take one was read from JDownloader for the protocol only.
- **yt-dlp**: `metadata::classify_failure` reads "--video-password" (its own hint, given only where an extractor takes one) as `PasswordNeeded { wrong: false }` and "wrong video password", "wrong password", "wrong passcode", "invalid (video) password" and "incorrect password" (`WRONG_PASSWORD_PHRASES`) as `wrong: true`, before the sign-in phrases (Vimeo's sign-in message names the account's `--password`, which stays a sign-in). `passwords::read_trying` sets `wrong` only when the person typed the password tried, so a saved one that stopped working just asks again. Tested live with Vimeo's public test video (`player.vimeo.com/video/68375962`, password `youtube-dl` from yt-dlp's own tests); `vimeo.com/68375962` itself needs a signed-in account in yt-dlp 2026.10.26.
- **Pending**: `PendingState::NeedsPassword` (saved as "password"; an older version reads it as waiting) with the error. `PendingLinks::unlock` sets the password and makes it waiting, and `readable` reads a waiting link with a password first. It never leaves by itself (`nothing_to_download` doesn't take it), keeps `start_when_read` (so a started link starts once unlocked), and `starts_with_all` and Download Right Away leave it. A password that opens it stays with it to the queue; one that doesn't is dropped.
- **Queue**: a run failing with `PasswordNeeded` goes back to Waiting and, once the known passwords are used up (below), gets `Recovery.needs_password` (`PasswordAsked`: whether its own password failed, and how many were tried by themselves), shown as `Hold::NeedsPassword { wrong, tried }`, which never ends by itself; `Recovery::after_failure` doesn't retry it and Try Now refuses it. `enter_password` saves the password with the item and starts it.
- **Tried before asking** (0.2.6; Fuzen's answer to `password-remember` on Open Decisions: the list first, then past passwords, saved only by choice and apart from the list, for links and archives alike): `passwords::known`'s `KnownPasswords`, which `DownloadQueue::open` makes from its database and settings and `DownloadQueue::passwords` hands to the preview card and Pending. **The list** is Settings → Passwords' Your Passwords, still `downloads.unpack.passwords` in `settings.json`, where it was while it was Archives' own. **Past passwords** are `past_passwords` in `tsundoku.db` (migration 19: `site`, which is `sites::site_of`'s key, `password`, `used_at`), written only while `DownloadSettings.save_past_passwords` (`savePastPasswords`, off to start with) is on, by `remember(link, password)`: never one the list has, and one kept already becomes the latest used. Turned off, they stay but are neither tried nor added to; `past_count` (each password once) and `forget_past` are Settings' line and Forget Past Passwords (the `past_password_count` and `forget_past_passwords` commands, `usePastPasswordCount`), and the UI never gets a past password. `for_link` gives a link's tries: the list in order, then its site's past ones, the latest first, none twice, `LINK_TRIES_AT_MOST` (20) in all, since each try asks the site again, and a site is never sent another's. `for_archive` gives an archive's, tried on this PC: the list, the download's own (`QueueItem.archive_password`, then `QueueItem.password`), then every past one, its site's first (`ArchivePasswords.listed` counts the list's).
- **A read that tries them** (`passwords::read_trying`, in `PreviewService::fetch` and `PendingLinks::read`): the link is read with its own password (the one typed, else the history's for the link), and when it answers `PasswordNeeded` and the person didn't just type that one, with each of `for_link`'s in turn until one opens it. None does: `PasswordNeeded { wrong: false, tried }`. Any other failure of a try ends them (a 429 starts the site's wait as usual), and so does a cancel; a typed password that fails is `wrong` with nothing else tried, since the known ones were tried before asking. The one that opened the link is `remember`ed; Pending keeps it with the link, and the preview card, which never gets a password it didn't type, leaves it for its download: `KnownPasswords::keep_for_download` by site and ID (in memory, the latest 50), which `DownloadQueue::password_for` takes after the one given and before the history's.
- **A download that tries them** (`DownloadQueue::try_next_password`): a run failing with `PasswordNeeded` drops the item's password (unsaving it if it was its own) and the item runs again with the next of `Recovery.password_tries` (`PasswordTries`: `for_link`'s without the one that just failed, made at the first such failure, in memory, and gone with the rest of `Recovery` on Resume and Retry, which try them anew). One being tried is only in memory; a run that finishes saves it with the item (`set_password`), the history and the past passwords. With none left it waits for the person, and a password they then enter that fails asks again (`wrong`) without new tries.
- **Archives**: `DownloadQueue::unpack_job` gives `UnpackJob.passwords` from `for_archive`, with `listed` and `opened` (`OpenedWith`, a callback, compared by identity): `unpacking::unpack_one` tells it a password past the list's that opened an archive, which the queue `remember`s for the download's site, and the log says "with password 2 from the list" or "with a password that isn't in the list", never the password. A failed download's password field (`FailureFixes`' `EnterArchivePassword`, a `PasswordForm`, given `onArchivePassword` by the queue's row only) calls `enter_archive_password` (`DownloadQueue::enter_archive_password`): the password stays with the item in memory (`QueueItem.archive_password`, gone once it finishes or the app closes) and the item is retried, which only unpacks. Before 0.2.6 that field added the password to the list; it never does now, and whether it's kept is Save Past Passwords'.
- **Kept as they are**: the list in `settings.json` and the past passwords in `tsundoku.db` are plain text, like each link's own. A backup's database copy has `past_passwords`, and a restore replaces this PC's with them (`backup::replace_history`).
- **Never written**: the yt-dlp log line goes through `passwords::hidden_in_arguments` (`--video-password <password>`, its abbreviations and `=` form too, a preset's own included); a file host's log names only the link. `DownloadReport.password` blanks it again in Copy Details, as a word of its own (`replace_words_ignoring_case`). Tests cover the log and the report (`runner::tests::gives_the_videos_password_but_never_logs_it`, `bug_report::tests`) and the queue item's JSON and `Debug`.

### What's New

- **After an update**: `src-tauri/src/whats_new.rs` embeds the root's CHANGELOG.md (`include_str!`) and answers `whats_new` with `core::changelog::whats_new`: the sections newer than `settings.lastRunVersion`, up to the running version, newest first (`changelog::sections` splits the file at `## <version>` headings, " · <date>" optional). With nothing to show, the running version is recorded at once; otherwise once the card is closed (`dismiss_whats_new`), so a start in the tray doesn't lose it. `note_start`, in `setup`, records the version at once on a first install (`ToolManager::needs_setup`), so its setup ends with nothing to tell; an install from before `lastRunVersion` existed shows only the running version's section. A restored backup keeps this PC's `lastRunVersion`. The UI's `WhatsNewCard` reads it once (`useWhatsNew`) and `ReleaseNotes` (`notes.ts`) shows the Markdown: headings, `- ` lists, paragraphs, bold, code and http(s) links, opened with `openWebPage`.
- **Before an update**: `AppUpdate.notes` is the updater's `body` (see Releases), shown by the update banner's What's New toggle; when it's empty, `releasePage` (the release's tag on GitHub) is linked instead. In a browser, `?update` shows the banner with stand-in notes, `?update=bare` without, and `?whatsnew` the card.
- **On demand**: Settings → About's What's New calls `AppActions.showWhatsNew`, which sets `App`'s `browsingWhatsNew`; `WhatsNewCard` then shows `BrowsedNotes` in place of the card an update left: the `release_notes` command's sections (`changelog::up_to`: every section up to the running version, newest first, which `changes_since` filters too; `useReleaseNotes`, read when it first opens), one at a time, picked from a select in the heading (`notes.ts`'s `sectionToShow`: the one picked, else the running version's, else the newest; `sectionDate` for each option's date). Which version is picked is the card's own state, so it starts over each time it's opened. Its × stops browsing and, when an update's card was waiting under it, dismisses that too (`dismiss_whats_new`). In a browser, the stand-ins' `releaseNotes` show.

### Running Programs

- `core::process` is the only place that starts yt-dlp, ffmpeg, Deno or gallery-dl. Each starts without a console window (`CREATE_NO_WINDOW`), suspended, is put in a new job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, then resumed, so it can't start anything outside the job. Ending the job ends yt-dlp and the ffmpeg it started; closing the job's handle (when the app exits or crashes) does the same.
- process-wrap was tried and dropped: its job object for `std` never sets kill-on-close, so the tools would outlive a crash.
- Every run is counted from just before it starts until it and everything it started have ended (`RUNNING_PROGRAMS`). Windows lets a folder be renamed while a program in it runs, so an install can't rely on the swap failing: `unless_running_from` does the swap only while no program runs from the tool's folder, and no program starts until it's done.
- Output is read line by line on two threads into a channel; a carriage return also ends a line. `run` polls every 100 ms for cancellation and its time limit.
- Tauri commands that run programs or download are `async` and do the work through `spawn_blocking`, since a sync command runs on the main thread and would freeze the window.

### Opening Files and Folders

- `src-tauri/src/shell.rs` is the only place that opens a file or folder, or shows a file in its folder: `show_in_folders` (Show in Folder everywhere, History's Show Selected in Folder), `open_folder` (Settings' Open Folder buttons, the download folder) and `open_file` (Open File, a post's files, Open in Editor for a log). Never call the opener plugin's `open_path`, `reveal_item_in_dir` or `reveal_items_in_dir` elsewhere.
- **Never open or reveal from a sync command.** Every command that does is `async` and runs it through `shell::in_background` (or `history.rs`'s `blocking`), off the window's thread and the async runtime's threads. Windows' shell can wait on a dialog: on Fuzen's PC, `HKCU\Software\Classes\Folder\shell` still made Directory Opus (uninstalled, its `dopusrt.exe` gone) the folder's default verb, so `ShellExecute` on a folder and `SHOpenFolderAndSelectItems` showed "Application not found" and waited until it was closed, and since those commands were sync, every other command waited too (found in 0.1.142). The plugin also returns `Ok` for most of `SHOpenFolderAndSelectItems`' failures, so `shell.rs` calls the shell itself (the `windows` crate) for folders.
- **Folders open in the default folder app, with File Explorer as the fallback** (0.1.144, Fuzen's ask; `shell.rs`'s `folder_app`, COM started single-threaded on the blocking thread for each call, `Com`). `open_folder` calls `ShellExecuteExW` on the folder with its default verb and `SEE_MASK_FLAG_NO_UI | SEE_MASK_NOASYNC`: when the verb's program is gone, it fails with `CO_E_APPNOTFOUND` and shows nothing (without the flag, it waits on "Application not found"). `show_in_folders` groups the files by folder (`by_folder`: in order, folders compared ignoring case) and checks each folder's default verb first (`folder_app::can_open`), since `SHOpenFolderAndSelectItems` shows that dialog itself with no flag to stop it: it reads the associations the shell uses for that folder (`SHCreateItemFromParsingName`, then `BindToHandler(BHID_AssociationArray)` for an `IQueryAssociations`), whose `ASSOCSTR_EXECUTABLE` answers `CO_E_APPNOTFOUND` when the program is gone (`ASSOCSTR_COMMAND` still names it) and `ASSOCSTR_DELEGATEEXECUTE` gives a COM handler; the verb can run with a COM handler (File Explorer's own verbs have one) or a program that's there (`verb_can_run`). Then `SHOpenFolderAndSelectItems` takes the folder's and every one of its files' IDs (`ILCreateFromPathW`), so all of them are selected. When either fails, `using_file_explorer` writes why to the app's output ("Opening <folder> in File Explorer: the default folder app is gone (Application not found (0x800401F5))") and File Explorer opens it: `%SystemRoot%\explorer.exe "<folder>"`, or `explorer.exe /select,"<file>"` with the folder's first file, since it takes one, started without waiting (Explorer hands the window to the running Explorer and exits with 1 even when it worked). The argument is written raw (`raw_arg`), the path quoted once (a comma is Explorer's separator; a Windows path can't hold a quote; `"D:\"` works), and a verbatim path loses its `\\?\` or `\\?\UNC\` prefix (`shell_path`), for the shell's calls too. A file still opens with `open_path`, the user's own association, unless it's a folder. Other platforms keep the plugin's way.
- **Trying it**: `shell::tests::folder_app_live` (ignored; `SHELL_LIVE_FOLDER=<folder holding two files or more>`) prints whether this PC's folder handler can open the folder, opening nothing, then points `HKEY_CLASSES_ROOT` at the machine's own classes for its process only (`RegOverridePredefKey`, nothing written), so the default path runs with the folder handler Windows ships whatever this user set: it shows the folder's first two files, both selected, and opens the folder above it, two File Explorer windows to close. On Fuzen's PC (2026-11-15) the user's handler is still the uninstalled Directory Opus (a backup of the keys is in `tsundoku\target\claude-scratch\show-in-folder`), so the app itself takes the fallback there; the live test showed the default path select both files and open its window with no dialog.

### Tools

- `core::tools::catalog` names each tool's release host, repository, release file and checksum file. gallery-dl (`mikf/gallery-dl`, the standalone `gallery-dl.exe`) comes from **Codeberg**, where its development moved in 2026: its GitHub releases since 1.32 have no files. Codeberg runs Forgejo, whose `/api/v1/repos/<repo>/releases/latest` answers in the same shape as GitHub's (`tag_name`, `published_at`, `assets` with `name`, `size` and `browser_download_url`), so `github.rs` reads both; its `SHA256SUMS` uses the `<hash>  <name>` form. Since 0.1.25 the first-run setup sets it up with the others (`ToolId::SETUP` is every tool, `setupToolOrder` in the UI), but like Deno it's optional: the setup can be left when only optional tools failed (`optionalTools`), and `needs_setup` asks only for yt-dlp and ffmpeg, so an install from before isn't sent back to it. It's run with `--config-ignore`, gallery-dl's spelling of yt-dlp's `--ignore-config`. ffmpeg comes from yt-dlp/FFmpeg-Builds' **shared** build (91 MB, 193 MB installed), not the static one (202 MB, 340 MB installed): ffmpeg and ffprobe share their DLLs instead of each carrying a copy. Everything in its `bin` folder is kept except ffplay.
- Checksum files come in two forms: `<hash>  <name>` lines (yt-dlp, FFmpeg-Builds) and PowerShell's `Hash : <HASH>` (Deno's `.sha256sum`). `checksum.rs` reads both.
- An install downloads to `tools\.download-<tool>\`, checks the SHA-256, unpacks to `tools\.new-<tool>\`, then swaps that folder in for `tools\<tool>\` (the old one moved aside, deleted after, put back on failure) once no preview, read or download runs the old copy: it waits up to 5 minutes (`ToolStage::Waiting`), then gives up with `ToolError::InUse`. Each tool has its own working folders, since the setup installs all three at once. Afterwards the tool is run (`--version`) to catch an antivirus quarantine.
- GitHub allows 60 API requests an hour per network without signing in. The latest release of each tool is cached for 10 minutes, so the setup's sizes and downloads cost one request per tool.
- yt-dlp updates itself with `--update-to stable@latest` (or `nightly@latest`). Naming the release, not just the channel, lets it go back from a nightly build to an older stable one, which plain `--update-to stable` refuses as a downgrade. It renames itself to `yt-dlp.exe.old` while updating and deletes that at its next update.
- yt-dlp and gallery-dl update themselves once a day (`ToolId::UPDATED_DAILY`): `tools::start_daily_updates` in the app crate runs `ToolManager::run_due_updates` at startup and every 10 minutes after, so a copy left in the tray for days is updated too. A tool whose last check (`ytDlpLastUpdateCheck`, `galleryDlLastUpdateCheck`) is a day old is updated, unless a program from its copy is running, which leaves it for a later look. The check is recorded even when the update failed, so a failing update isn't retried at every start, but not when it gave up because the old copy stayed in use. gallery-dl updates through the app's own install (`update_gallery_dl`, also Settings' Update Now), only when the latest release's SHA-256 differs from its copy's: its own `--update` looks for GitHub releases, which have had no files since it moved to Codeberg.
- Settings → Tools' Update All (`update_all_tools`, `ToolManager::update_all`) runs each managed tool's update in turn, yt-dlp through `update_yt_dlp` and the others through `update_to_latest`, and answers a `ToolUpdateOutcome` for each (`updated`, `upToDate`, `failed`), skipping the user's own copies; a failure doesn't stop the rest. The cards follow through `tool-progress`, and a card forgets a found update once its copy's version changes.
- ffmpeg, Deno and gallery-dl are compared by the SHA-256 of the release file they came from, stored in `settings.json`. FFmpeg-Builds rebuilds daily under the rolling tag `latest`, so its releases are labelled by date. A copy adopted from `tools\` at setup has no stored checksum, so its first check always offers an update.
- Progress reaches the UI as `tool-progress` events (`ToolProgress`); every install or update ends with one whose stage is `null`. `tools-changed` tells the UI a tool changed on its own (the daily update of yt-dlp or gallery-dl).
- A tool's errors reach the UI as `ToolError`, a tagged union; `errors.ts` turns each kind into a sentence from `strings.ts`, with the technical `detail` underneath. `PreviewError` and `HistoryError` work the same way.

### Metadata and Preview

- `metadata::normalize_link` accepts only http and https links with a host (adding `https://` when there's no scheme), so pasted text, a search (`ytsearch:`) or a file path never reaches yt-dlp. The link is also passed after `--`, so nothing in it can be read as an option.
- yt-dlp runs as `--ignore-config --no-playlist --flat-playlist --dump-single-json --encoding utf-8`, with `--js-runtimes deno:<path>` when Deno is set up (`--no-js-runtimes` otherwise, so a Deno on PATH can't hide that it's missing) and `--ffmpeg-location`. `--flat-playlist` makes a playlist or channel answer at once instead of reading each video; `--encoding utf-8` keeps its messages from being mangled by the Windows code page. The Deno path must be a Windows path: yt-dlp silently ignores a `/d/…` one.
- The site is yt-dlp's `extractor_key` in lowercase, as yt-dlp's archive writes it (`youtube`, `soundcloud`, `archiveorg`), and with the video ID it's what the duplicate check matches on. A format counts as video when it has a height and isn't `vcodec: none`, since some sites (archive.org) give no codec.
- yt-dlp reports a failure as its last `ERROR:` line; `classify_failure` sorts it into a `PreviewError` by phrases in it. Upcoming premieres are errors too ("This live event will begin in…"), not a field of the answer. When a site's message changes, add the new phrase and a test.
- **Two tools read links.** `sites::prefers_images` sends image sites (Instagram, X, Bluesky, Pixiv, Tumblr, boorus…) to gallery-dl first and everything else to yt-dlp; `preview::read_link` then falls back to the other tool when the first answers "unsupported" or yt-dlp finds no video (`PreviewError::NoVideo`), or when gallery-dl fails to read a site it knows. A missing sign-in or an unavailable post isn't retried. yt-dlp's refusal of a site it dropped as used for piracy ("primarily used for piracy": GoFile since 2026) is `UnsupportedSite` too, so gallery-dl, which still reads GoFile, is asked next. Without gallery-dl, a photo post is `ImagesNotSetUp`, which the UI offers to fix. The user is never told which tool read a link (the user's choice: tools are internals), so preview errors don't name yt-dlp.
- `gallery::fetch` runs `gallery-dl --config-ignore --dump-json -- <link>`. Its answer is a list of messages: `[2, post]`, `[3, url, file]` per file, `[6, url, …]` for a link elsewhere (a profile's posts), and `[-1, {error, message}]` for a failure, which still exits 0. `sort_answer` groups the files under their post (a `[2]` naming the same post again doesn't start another); an answer of several posts, or of links elsewhere only, is a page that can't be read as one post and is refused as `NotListable`. Only an unsupported link exits non-zero (64). Signed out, Instagram redirects to its login page and X refuses media timelines, so both need cookies even for public posts. Instagram's API may instead answer with a `KeyError` about a field ending in `_connection` (`'xdt_api__v1__…_connection'`), which only a signed-in answer has: `classify_message` sorts it as a sign-in (`missing_signed_in_field`), not as the dropped connection its word suggests, so it's never retried by itself, and no other `KeyError` counts as a network error either (they're site errors).
- **Files that are neither images nor videos** (a .zip or .pdf on Pixeldrain, Gofile, Bunkr or Cyberdrop, which gallery-dl reads as a post of one file): `gallery::kind_of` sorts each file by its extension (`VIDEO_EXTENSIONS`, `IMAGE_EXTENSIONS`), then its `mime_type`; one without an extension stays an image. Others count in `PostContents.others` (`#[serde(default)]`, so posts saved before read as 0), shown as "1 file", get no thumbnail (their address is the file itself, which the card would fetch whole), and a post of one such file with no caption or uploader is titled by its `name` (`lone_file_name`). The history keeps only `post_images` and `post_videos`, so such a download shows no contents there. ### File Hosts

- MEGA, MediaFire, Google Drive, Dropbox, OneDrive, pCloud, WeTransfer, the Internet Archive, Yandex Disk, Box, Icedrive, 1fichier, SwissTransfer, Files.fm, upload.ee, TransferNow and Filemail, and the sites read through the check window (Workupload, Buzzheavier: `window_sites`), are read and downloaded by Tsundoku itself or its check window (`core::hosts`, `downloads::file_runner`), with no tool, through `reqwest`. `hosts::Host::of` picks them by domain before yt-dlp or gallery-dl is asked, in `PreviewService` and in `ToolRunner` (a job with `files` set). Like the tools, the host stays out of the UI's words, except as the site's name.
- **Adding a host**: each host's module holds its `FACTS` (`HostFacts`: name, history site, domains, whether it sends attachments, its `read`, its `page_error` when its pages say more than their status, and `download_file_id` when a download link of its own can be pasted, as MediaFire's), its file source type and its `address` when it has one. Every request it sends goes through `send_checked(FACTS.name)` (`hosts::SendChecked`), never a bare `send`. `Host` then needs the variant, a line in `BUILT_IN` and in `facts`, and `FileSource` a variant. Supported Sites, `{site}`, `sites::site_of` and the clipboard watcher follow `Host` by themselves.
- A host's reader turns a link into a `Share`: the file or folder's ID and name, and its files (`RemoteFile`: path inside the download's folder, size, `FileSource`). The preview sees it as a `VideoInfo` with `files: Some(FileContents)` (count and bytes, migration 4: `videos.file_count`, `file_bytes`). The download reads the link again, since download addresses expire, and asks each file's address just before fetching it.
- **MEGA**: the key is the part of the link after `#`, never logged. The API is `POST https://g.api.mega.co.nz/cs?id=<n>[&n=<folder>]` with a JSON list of commands: `{"a":"g","p":<file>}` (or `"n"` inside a folder) for a file's size, attributes and address (`"g"`, missing once the transfer quota is used up), `{"a":"f","c":1,"ca":1,"r":1}` for a folder's nodes. A file's 32-byte key XORs into the AES-128 key; bytes 16–24 are the counter's nonce and 24–32 the meta-MAC. Contents are AES-128-CTR (seekable, so a part file resumes), names AES-CBC with a zero IV (`MEGA{json}`), folder nodes' keys AES-ECB under the folder key. A node's `k` can hold several `handle:key` pairs separated by `/`, and the link's key opens only the one under the shared folder's own node (the folder whose parent isn't listed, `share_root`): that one is tried first, then the rest, and a node none of them opens is left out with what's inside it. The check is MEGA's chunked CBC-MAC (chunks of 128 KiB growing by 128 KiB to 1 MiB), folded to 8 bytes. Error -3 (busy) is retried with backoff, then is a network error like -18; -2/-9 (missing), -11 (access refused) and -16 (taken down) are Unavailable; -4/-6/-17 are LimitReached. **Its transfer quota** (0.2.8): once a connection's is used up, MEGA says for how long, as `tl` (seconds) in the `g` answer, which then has no address or `e` -17, or as `X-MEGA-Time-Left` on its download server's 509 (both as MEGA's SDK reads them; `AddressAnswer::address`, `mega::quota_wait`, which `file_runner::fetch` asks on MEGA's failed answers): that's `PreviewError::WaitBetweenDownloads`, so the download waits exactly that long plus a minute, as for 1fichier, instead of guessing from 30 minutes. A quota with no time (0 or none) stays `LimitReached`. MEGA's download servers answer `Range` with 206 (checked 2026-11-21), so a part file resumes. Test vectors in `hosts/mega/tests.rs` come from async-mega-py (Apache-2.0); GPL code (megatools, gallery-dl) was read for the protocol only.
- **MediaFire**: `file/get_info.php`, `folder/get_info.php` and `folder/get_content.php` (API 1.4, `response_format=json`, files and folders separately, 1000 a chunk) list a share with sizes and SHA-256s. The address is the file page's Download button (`a#downloadButton`'s `href`, or its base64 `data-scrambled-url`); a page that answers with the file itself is used as it is. Some files' pages redirect to `?action=check`, which Cloudflare answers with 403 and its browser check; Tsundoku doesn't try to pass it (`check::is_browser_check` makes it `PreviewError::BrowserCheck`), and the download waits for the person (below). That address (`download<n>.mediafire.com/<token>/<key>/<name>`) is also taken as a link, since userscripts and download managers' add-ons copy it: `parse_link` reads the file by its key and keeps the link as `MediaFireFile.direct`, which `address` probes first (`hosts::probe`) and downloads from while it gives the file, asking the page only once its token has run out.
- **Checks only a person can pass** (`hosts/check.rs`, `downloads/holds.rs`, `downloads/window_offer.rs`, `src-tauri/src/check_window.rs`; Fuzen's answers on Open Decisions and in the thread: show the check, let it be skipped, and catch it the same way for every site rather than host by host): Cloudflare's challenge, `cf-mitigated: challenge` or a 403/503 with `_cf_chl_opt` or its "Just a moment..." title (`check::is_browser_check`), is `PreviewError::BrowserCheck`. While the window is open for a download, every address it or a window it opened goes to (or downloads from) is written to that download's log (`note_address`; addresses only).
- **Known window sites** (`hosts/window_sites.rs`; Fuzen's answer in the thread: only for known sites, so supported and unsupported links don't mix): sites read only through the check window, as `Host::Window(WindowSite)`, which Supported Sites, `{site}`, the history and the clipboard watcher see like any host. An entry is a name, its history site, its domains (its file servers' too when they're another domain) and its file links' shape (`LinkShape`: paths with `{id}`, the page, the ID's least length), never anything about its pages; its `read` only asks the page for a 404 (a deleted file) as Tsundoku, and the link reads as one file named after its ID, "Size unknown" (`formatContents`), until its download starts. **When a site needs a reader**: its files can be listed or downloaded with Tsundoku's own client (an API, a page that answers as Tsundoku), or it holds folders; a module in `hosts` with its `FACTS`, as above. **When an entry is enough**: its link's own page is behind a check Tsundoku won't pass and holds one file. **An entry needs a real test first**: a real link of the site, downloaded once through the window with a person's click, before it's added; a link from a site that is neither a host nor an entry stays unsupported and is never offered the window. Entries: **Workupload** (`workupload.com/file/<id>`: a proof of work its page runs; tried 2026-11-11, its file server answering only the window's session, so the window saved it) and **Buzzheavier** (`buzzheavier.com/<id>`, `/f/<id>`: Cloudflare's check on its page for Tsundoku's client; tried 2026-11-12, its file server answering Tsundoku with the file after an advert's pop-up on the first click).

- **Picking a shared folder's files** (0.1.132; the thread "Pick files inside shared folders"): `Share::video_info` lists a share of more than one file as `VideoInfo.shared_files` (`SharedFile`: `path`, the share's path joined with "/" by `hosts::shared_path`, `size` and `picked`, true to start with; not serialized when empty, so optional in TypeScript), in the share's order. `VideoInfo.files` stays the whole share (the rules' `is_one_file`, the history's `file_count`, the card's header). `VideoInfo::picked_shared_files` (the paths picked, `None` for every file) becomes `JobSpec.picked_files`, and `picked_contents` (the count and bytes picked, else `files`) sizes `room::expected_bytes` and the run's progress. `insert_post` refuses a folder with every file unticked (`NothingPicked`). `file_runner::taken_files` picks the files by path, two of one path together, each keeping its index in the whole share for its part file; a path the folder no longer has is logged and skipped, and none left is `DownloadError::PickedFilesGone`, never the whole folder. `JobOutcome::Finished.shared` gives the share paths of the files the run took (a file saved as "Name (2).zip" can't be traced from its saved path, nor an archive from what unpacking left in its place, so `unpacking::DownloadedFiles.shared` carries them through unpacking, a stopped one's Retry included), which `DownloadQueue::record` passes, each once, as `NewDownload.share_paths` into `downloads.share_paths`, a JSON list (migration 16; NULL for downloads before, which took every file, and for videos and posts). `History::left_out_shared_files` (the `left_out_shared_files` command, `useLeftOutSharedFiles`) gives the places in `shared_files` no download took (a file the owner added since too), `None` when one was made before share paths were kept, when nothing is left out or when it was never downloaded. The preview card ticks those (`defaultSharedPick`, `withSharedPicked`); `PendingLinks::read` ticks them for a pending link (`with_left_out_ticked`) and `set_shared_files` (`set_pending_shared_files`, by place) saves new ones. The list (`SharedFilesList`) builds its tree from the paths (`sharedTree`, dropping the one folder every file is in), folds folders above `FOLDED_ABOVE` (200) files, filters by the path from its top, and draws only the rows on screen (`useVirtualRows`, every row 28 px so none is measured); its rows' handlers read the latest picks through a ref, so a tick redraws only what it changes. Tried with 10,000 stand-in files (`?folder=10000` in a browser): a tick takes about 10 ms.
- `file_runner` saves each file to `<temp folder>\<n>.part`, resuming with a `Range` request when the host allows it (206), decrypting MEGA's on the way, then checks it (MAC, SHA-256 or SHA-1; Google Drive and Dropbox give only the size), deleting a damaged one (`DownloadError::Damaged`), and moves it to its place with a free name (`Name (2).ext`). A file already at its place with the same size is skipped. Progress is one meter for the whole share, paced to the speed limit. For Google Drive and Dropbox, an answer without `Content-Disposition: attachment` is a page about an error (`Host::page_error`), never written into the part file.

### History

- `tsundoku.db` is SQLite (`rusqlite`, bundled), in WAL mode with foreign keys on, shared by the history and the queue through `database.rs`. Migrations are SQL strings there, applied in order and counted in `PRAGMA user_version`; never change a released one, add one. A database from a newer version is refused rather than read.
- `videos` holds one row per site and ID (with `post_images` and `post_videos` for a post); `downloads` one row per finished download, removed with its video (`ON DELETE CASCADE`); `downloads.share_paths` the paths in the share of the files a file host's download took (a JSON list, migration 16, NULL before 0.1.132 and for videos and posts); `download_files` every file of a download that made several (a post) or of a file host's link, with its number in the post (`post_number`, NULL for posts downloaded before it was kept), removed with its download. A video's download has no `download_files` rows: its `file_path` is the file. Times are seconds since 1970.
- `archive.txt` is rewritten whole (atomically) after every change and when the history opens, in the order videos were first downloaded.
- The UI names a download by its ID to open it or show it in its folder, never by a path, so it can only open files the history recorded.

### History View

- The history view is a list of cards, not a table: the window's minimum width (760 px) can't fit eight columns and a readable title. Sorting is a select with a direction button; it covers every column `HistorySort` has.
- **Groups** (0.2.13, Fuzen's ask: like Downloads): `HistoryQuery.group` (`HistoryGroup`: none, site, destination, uploader, month) makes the core order each group's videos together before the sort (`HistoryGroup::row_order`, in `page` and `ids`), and `History::groups` (the `history_groups` command, `useHistoryGroups`) gives the groups in that order with their counts (`HistoryGroupCount`: `key`, `label`, `count`). Site goes by `v.site`, named and ordered by its videos' `site_name`; Folder by the latest download's file's folder (`DOWNLOAD_FOLDER`: `rtrim` takes the file's name off, ignoring case); Uploader by `lower(uploader)`, the videos without one last (`key` null, "No Uploader"); Month by the latest download's local month, newest first unless sorted by date downloaded oldest first. The arrangement (`group`, `sort`, `descending`) is `ListArrangements.history` (`HistoryArrangement`, `useHistoryArrangement`), kept like the other lists'. The UI (`historyList.ts`) places each group by the counts before it (`historyGroups`: `start`) among the videos read, and lays out entries (`historyEntries`): a heading once a group's first video is read, its rows (or blocks of `LINES_PER_BLOCK` lines of pictures, so a block is drawn whole and Masonry's columns start level at each), stopping after a group not read whole; a folded group keeps its heading. The entries are only rebuilt while the pages and the groups answer the same query and agree on the total, so a new query never pairs one's pages with the other's groups.
- **Thousands of rows**: it reads its results a page at a time (`History::page`, 100 videos from an offset, with the total for its count; `useHistory` is an infinite query that reads the next page while what's read ends within 3,000 px of the screen, `LOAD_AHEAD`), and draws only the rows on screen and 600 px around them (`useVirtualRows` in `virtualRows.ts`). The rows not drawn are two spacers, so the rows drawn stay in the normal flow: each is measured by a `ResizeObserver` (the 12 px between rows is its own padding, so it's measured too), and when a row above the screen changes height, Chromium's scroll anchoring keeps the screen still. Spacers rather than padding, which is a suppression trigger for scroll anchoring on an ancestor. Which rows are expanded is kept in the view, so a row scrolled away comes back as it was. The search waits 250 ms after typing (`useDebouncedValue`). TanStack Virtual was tried and dropped: `react-hooks/incompatible-library` warns on its `useVirtualizer`.
- Whether files are still there is checked for the page read only, once the database lock is released (`PastDownload::with_file_checked`), not for the whole history. With 5,000 videos (`history::tests::measure_at_scale`, ignored, run with `--ignored --nocapture`), a page takes about 15 ms against 400 ms for the whole list, and the view opens in about 20 ms against 1.5 s.
- **Size on disk** (`History::size`, the `history_size` command, `useHistorySize`): every file of every download of the videos the query matches (`download_files`, else `downloads.file_path`), each path once ignoring case, that's still there, with how many and how many are missing (`HistorySize`), shown after the count. `size_on_disk` groups the paths by folder and reads 8 folders at a time: a folder of up to `ASKED_ONE_BY_ONE` (4) of them asks about each file (`fs::metadata`), one with more is listed once (`read_dir`, whose entries carry their size on Windows), so a slow or network drive answers once a folder rather than once a file. With `files` set it runs `note_missing` first, as `ids` does. The UI reads it under the history's query key, so it's counted again with the list (a finished download, Forget, Move Files…, reopening the view), keeping the last answer faded while a new query's is counted. With 5,000 videos (`measure_at_scale`, release), about 11,000 files take 33 ms in one folder and 160 ms at three a folder; in a debug test copy, 5,005 items' 9,681 files took 85 ms.
- **Tsundoku's own data** (`DataPaths::history_data`, the `history_data_size` command, `useHistoryDataSize`): what the data folder holds for the history, as `HistoryData`: `tsundoku.db` with its `-wal` and `-shm` (shared with the queue, Pending and Watched), `thumbnails\` and `logs\` (`folder_contents`, subfolders included, links not followed) with their counts, and `archive.txt`. The tools, their caches, the settings, the check window's profile and backups aren't counted. It's for the whole history, not the query, at the count line's right end, read under the history's query key as the size is. With 5,000 thumbnails it takes under 15 ms in a debug build.
- Its results refetch when a download finishes (a queue item turns done) and after Forget. Every page shown is read again, from the first, so they stay in step.
- **Filters** run in the core with the paging (`filter_of`): Kind matches any download of the video (`downloads.kind`, migration 8, written by the queue from `RuleSubject::kind`; downloads from before are worked out from the video and the format, and from the preset's name when the format names no codecs), the date range the latest download's date (`downloaded_from` inclusive, `downloaded_until` exclusive; the UI works the bounds out when a range is picked, `historyDates.ts`, so the query doesn't move). The Files list (`HistoryQuery.files`, `FileState`) matches the File Missing pill, or its opposite: the latest download's file. Whether a file is there is only known from the disk, so the first page of a query with `files` set (`offset` 0) and `ids` check every video the other filters take (`note_missing`, 8 threads) and write the missing ones to `temp.missing_files`, a table that lives only while the app runs; later pages go by it, so they stay in step with the first.
- **Ticked rows**: Pending's pattern, a tick box per row and one for them all with the count. Ticking them all asks the core for every matching ID (`history_ids`), not only the rows read. What's ticked belongs to the query: a new search or filter starts with nothing ticked, so a ticked row the new results hide can't be forgotten unseen. Forget Selected asks once and calls `History::forget_all` (one transaction, `archive.txt` rewritten once); Show Selected in Folder counts the folders first (`history_folder_count`, ignoring letter case), says so when no file is left, asks when there are more than 5, then `show_videos_in_folders` passes every file to `shell::show_in_folders`, which opens each folder once with its files selected (only the first when it falls back to File Explorer, whose `/select` takes one).
- **Moving files** (`History::move_files`, the `move_history_files` command, `core::relocate`): every file of every download of the videos (`download_files`, else `downloads.file_path`) that's still there goes into the folder picked, relative to `relocate::common_folder` of its download's files, so subfolders come along. `relocate::move_file` makes the folder, takes a free name (`downloads::free_name`, " (2)"), and copies then deletes when `rename` fails (another drive), keeping only one copy if the delete fails. The rows' paths are updated in one transaction (`downloads.file_path` where it was the old path, so a post's first file follows too). `MovedFiles` counts moved and missing files and lists failures (`FailedMove`). Folders left empty stay.
- **Kept thumbnails** (`core::thumbnails`): a row shows the thumbnail kept in the data folder's `thumbnails\`, else the site's picture, else the empty tile (`Thumbnail`'s `fallbackUrl`), since sites' links expire (Instagram signs its image links) or go with a deleted post. Each is a 224×126 JPEG (twice the row's 112 px, cropped to 16:9 as the row shows it, about 6 KB) named `<site>-<16 hex of SHA-256 of site and ID>.jpg` (`file_name`), held in `videos.thumbnail_file` (migration 10: NULL until made, "" when none can be). The worker (`Thumbnails`, started in `open_data`) settles the folder with the history once at startup (a name whose file is missing, as after restoring a backup, is made again; a file no video names is deleted), then makes what's missing, newest first, every 15 seconds and a quarter of a second apart, so a new download gets its thumbnail within seconds and older rows follow. Sources, best first (`History::needing_thumbnails`): a post's first file, then its picture on the site; a video's or song's picture on the site, then a frame (or the cover art) of its own file; none for a file host's files. `FfmpegMaker` reads a site's picture with `hosts::client` (a 4xx means it's gone) and runs Tsundoku's ffmpeg: `thumbnail=30` picks a representative frame among the first 30, then it's scaled to cover 224×126 and cropped, written beside the target and renamed. A video none of whose sources can ever work gets ""; one that might later (offline, ffmpeg not set up) is tried again at the next start, not before. Forget deletes the file (`History::with_thumbnails_folder`). The window reads them through the `thumbnail` protocol (`history::serve_thumbnail`, `http://thumbnail.localhost/<name>` in WebView2, `keptThumbnailUrl` in `api.ts` through `convertFileSrc`), which serves only names `thumbnails::is_file_name` accepts, from that folder; the CSP's `img-src` allows it.
- Download Again in the history opens the video's preview (`AppActionsContext.showLink`, which also keeps the link as the add bar's field's text), so the preset is picked and the duplicate warning shown as for any link.

### Presets and Downloads

- [Download Pipeline](./DOCUMENTATION/Docs/Download%20Pipeline.md) covers the queue's states, yt-dlp's arguments, the progress lines, temporary folders and logs.
- Presets live in `settings.json` (`presets.list`, `presets.defaultId`); the four built-ins have fixed IDs and can be reset, others are `custom-<n>` (`next_custom_id`). The default is always first: `PresetManager::overview` and `set_default` put it there (`default_first`), and `move_to` (the `move_preset` command) never places a preset above it. Any preset but the default can be deleted (`PresetError::IsDefault`), the built-ins included; `PresetsOverview.removed_built_ins` lists the deleted ones, which `reset` puts back at the end. `add` (`add_preset`) adds one set up as Best Video ships. `Preset::to_args` gives a preset's yt-dlp arguments, and both the editor and the queue use it.
- Extra arguments are split on spaces with double quotes grouping, backslashes left alone for Windows paths. Options that would break progress, paths, the history or the single-video rule are refused, abbreviations included, since yt-dlp accepts them (`--outp` for `--output`); `--progress` is allowed though it begins `--progress-template`.
- A queue item stores a copy of its preset and its resolved folder, so editing a preset or the download folder later doesn't change it.
- **A folder picked for one download** (migration 11): `pending_links.folder` (`PendingLink.folder`, `PendingLinks::set_folder`, the `set_pending_folder` command) goes with the link when it starts; `add_in`, `add_post_in` and `QueuePick.folder` take one for the queue, and `DownloadQueue::set_folder` (`set_queue_folder`) changes a waiting, stopped or failed item's, deleting its temporary folder when the folder changes, since it lives in the destination. Either wins over the rules (`chosen_folder`: a folder that isn't a full path is inside the download folder), and `QueueItem.folder_chosen` (`queue_items.folder_chosen`) remembers it. The UI shows it as `DestinationSource::Chosen` ("Picked for This One"); `DestinationLine`'s `onChoose` picks and drops it.
- **A rule picked for one link** (migration 14; Apply a Rule… in Pending, on the preview card and in Test a Link, whose `add_to_queue`, `add_post_to_queue` and `rule_unpacking` take a `ruleId` since 0.2.7): `pending_links.rule` (`PendingLink.rule_id`, `PendingLinks::set_rule`, the `set_pending_rule` command) goes with the link when it starts (`add_in` and `add_post_in` take a `rule_id`), and `queue_items.rule` (`QueueItem.rule_id`) keeps it, so `DownloadQueue::set_folder(None)` gives its folder back. `rules::picked_rule` finds it by ID: `destination`, `start_preset` and `file_name` take it (`picked`) and let it decide what it sets before any other rule, whatever its conditions and even while it's off; what it doesn't set goes to the rules as usual. Its `{1}` to `{9}` take nothing when its pattern doesn't match (`captured_when_picked`). A picked folder still wins over it. `download_destination` and `rule_preset` take a `ruleId`; in the UI, `DestinationRequest.ruleId`, `useRulePresets`'s `ruleIds`, and `DestinationLine`'s `chosenRuleId` and `onChooseRule` (a `Menu` of every rule, `Undo2` for Use the Matching Rules), which names the rule picked by comparing its number with the destination's source. The Queue's group by rule passes `QueueItem.rule_id`.
- **Manual rules** (0.2.7, Fuzen's ask; Rules' Manual Rules list): `FolderRule.manual` (`#[serde(default)]`; a version from before reads one as an automatic rule) is a rule only ever applied by hand: `FolderRule::applies_by_itself` (on and not manual) is what `destination`, `start_preset`, `right_away_rule`, `unpacking_rule` and `file_name` ask of every rule but the one picked, so a manual rule decides only as `picked_rule`, whatever its conditions, and its Matches patterns fill `{1}` to `{9}` (`captured_when_picked`: none when its pattern doesn't match that link). `with_catch_all_first` keeps them after the other rules, in their order, on and without `download_right_away` (decided before anything is picked), and the catch-all never manual, so the UI's two lists are runs of the one list and rule numbers stay one sequence. The UI (`RulesView`) splits the list at the first manual rule, moves a rule only within its list, and moves it across with `manual` (the core then puts it first among the manual rules, or last among the others); Apply a Rule…'s `Menu` lists the manual rules first under their heading (`MenuItem.group`). Their sections are `RULES_SECTION_IDS` (`ruleLabels.ts`). A manual rule picked for a link its conditions don't match still applies (Fuzen's answer to `manual-rule-not-matching` on Open Decisions, 0.2.11), with a warning: `destination` gives `Destination.picked_mismatch` (`PickedMismatch`: the rule, and `nothing_captured` when its pattern found nothing, so `{1}` to `{9}` have no value; never for an automatic rule picked by hand, which is picked because it doesn't match), and `DestinationLine.tsx`'s `PickedRuleWarning` shows it as a `warning` status message under the folder line on the preview card, in Pending and in Test a Link.
- **Where a download goes**: `rules::destination`, through `DownloadQueue::destination`, which both adding and the preview card (`download_destination`) use. The last rule that's on, picks a folder and whose conditions all match gives the folder (the bottom-most in the Rules view); else the preset's own folder (`Preset::own_folder`); else the download folder, `DownloadSettings::resolved_folder`: the chosen folder or `settings::default_download_folder` (`Downloads\Tsundoku`). `PresetsOverview.default_folder` carries the download folder to the preset editor, so Settings refetches the presets and destinations after changing it.
- **Folder rules** live in `settings.json` (`rules.list`), in order. Each condition joins the one before it with `RuleCondition.join` (`ConditionJoin::All` for AND, `Any` for OR, `#[serde(default)]` AND; the first's is ignored). OR binds first (`FolderRule::matches`): conditions joined by OR form groups, one of which must match, and every group joined by AND must, so "A OR B AND C" is (A or B) and C, which is how Fuzen reads it. 0.1.89 and 0.1.90 had one join for the whole rule (`FolderRule.join`, now read only: `#[serde(skip_serializing)]`, `#[ts(skip)]`), which `with_joins_on_conditions`, in `with_catch_all_first`, moves onto each condition. A rule without conditions matches every download. Conditions compare text ignoring case (unless `RuleCondition.case_sensitive`, `#[serde(default)]`, which `minds_case` ignores for the kind and the preset; a pattern then compiles without `case_insensitive`) and the spaces around the value, against every name the download's value goes by: a site matches its extractor key (`twitter`), its domain (`x.com`) and its `SIGN_IN_SITES` name (`X`); a preset its ID and its name. An uploader is its name (`uploader`) and its handle (`account`: yt-dlp's `uploader_id` through `metadata::handle`, which drops the "@" and leaves out numbers and YouTube channel IDs; gallery-dl's field for each site in `gallery::account`, the same ones as `post_names`). A missing uploader never equals, contains or matches anything. `RuleField::Tags` compares each tag's name and English name (`RuleSubject::values`); its Is and Is Not take a list, one tag a line (`RuleCondition::listed_values`), which the UI shows as Has and Doesn't Have with a `TagInput` (`ruleLabels.ts`'s `takesTagList`, `tagList`, and `withOperator`, which turns the list into its first tag and back when the comparison changes). Matches and Doesn't Match (`RuleCondition::is_pattern`) compile the value with the `regex` crate, ignoring case (`RegexBuilder::case_insensitive`), and look for it anywhere; `validate` refuses a pattern that doesn't compile as `RuleError::InvalidPattern`, with the crate's one-line reason (`pattern_problem`), and one that slipped in anyway matches nothing. `rules::placeholder_value` fills a folder's placeholders in any case: `{site}` (`rules::site_name`: the sign-in name, else the file host's name, else the extractor key), `{uploader}`, `{account}` (else the uploader), `{playlist}` (`VideoInfo.playlist`, else No Playlist), `{title}`, `{id}`, `{kind}` (`DownloadKind::folder_name`), `{preset}` (the kind's name without one), `{year}`, `{month}` and `{date}` from `upload_date`, `{added}` (the local date, `local_date`; tests pass one to `destination_on`), `{tags}` (every tag's name, joined with ", ", No Tags; `metadata::tag_list`), Pixiv's `{tagsJa}`, `{tagsEn}` and `{tagsBoth}` (`TagLanguage`: as written, English where given, or "原神 (Genshin Impact)"), `{rating}`, `{workType}` and `{series}` (from `VideoInfo.pixiv`, `PixivDetails`, 0.2.20: gallery-dl's `rating`, `type` and `series.title`), `{ai}` ("AI" for `illust_ai_type` 2, else left out whatever Missing Values says), `{pages}` (`rules::file_count`: a post's files picked, or a share's), `{tag}` (`FolderRule::matched_tag`, in `FillIn.tag`: the tag found by the first of the rule's Tags conditions with Is, Contains or Matches that found one, `RuleCondition::found_tag`, Is giving the condition's own spelling of the first of its list the download has; a rule without such a condition leaves `{tag}` as it is, as `{1}` without a pattern), and `{1}` to `{9}` from the rule's first Matches pattern with groups (`FolderRule::captured`), each made safe as one folder's name and cut to 80 characters (`folder_part`), with Unknown (Untitled, or the kind) for a missing value; other braces, and `{1}` in a rule without such a pattern, stay. **Missing values** (0.1.102, Fuzen's ask: `{site}\{account}` saved a MediaFire file in `MediaFire\Unknown`): `FolderRule.missing_values` (`MissingValues`, `#[serde(default)]` `StandIn`, so rules saved before keep Unknown) set to `LeaveOut` makes `placeholder_value` answer `NamePart::Value(None)` for a missing value instead of the stand-in. `fill_placeholders` fills the folder one name at a time between separators (`fill_folder_name`): a name whose placeholders all have no value goes with its separator (`{site}\{account}` is `MediaFire`, `D:\{account}` is `D:\`), one with some keeps them, each missing one going with the text before it, or after it when it's the first (`name_parts::join_leaving_out`, the rule posts' names already had for an unknown date), and an empty result is the download folder (`inside_download_folder`). In `StandIn` the output is what it was. A watched source's Save In (`filled_folder`) always uses `StandIn`. A folder that isn't absolute is joined to the download folder. The catch-all (`catch-all`, no conditions, `{site}` to start with) is always first, so every other rule overrides it, and comes after a preset's own folder: `rules::destination` takes the last matching rule other than it, then `Preset::own_folder`, then the catch-all when it's on, then the download folder. **Order**: since 0.1.86 the last matching rule decides (Fuzen's choice, so a rule added at the bottom overrides those above it); before, the first one did, with the catch-all last. `RulesSettings.last_wins` (`lastWins`, missing in a file from before) tells them apart: `Settings::from_json` reverses a list without it, so each rule keeps deciding what it did, and sets it. An older version reads a list saved since as first-wins, so its rules then decide in reverse. `rules::with_catch_all_first`, applied when settings are read and in `RuleManager::save`, moves it to the top, drops any conditions, turns the posts rule of 0.1.11 to 0.1.29 (`posts`, "kind is post → {site}") into it, keeping its folder and whether it's on, and puts it back turned off if it's missing, so it can't be deleted; the Rules view adds new rules at the bottom, doesn't offer to move, duplicate or delete it, and its editor has no conditions. `Settings::from_json` turns a saved `downloads.postsFolder` (0.1.8 to 0.1.10) into a "kind is post" rule (`rules::posts_folder_rule`) below the catch-all when the file has no `rules` yet. `RuleManager::save` replaces the whole list, trimmed and checked, and gives new rules (an empty ID) `rule-<n>`.
- **Names**: `FolderRule.name` (`#[serde(default)]`, trimmed when saved, empty for none). - **Automatic retries** (`downloads/holds.rs`): a run that fails with `PreviewError::Network` or `LimitReached` goes back to Waiting with its own wait instead of Failed (`finish`, `Recovery::after_failure`): a lost connection after `CONNECTION_RETRY_WAITS` (30 s, 2 min, 8 min), then it fails; a used-up download limit after `limit_wait` (30 min doubled up to 4 h, `LONGEST_LIMIT_WAIT`), never failing. `QueueItem.recovery` (`#[serde(skip)]`, `#[ts(skip)]`) counts both and holds the wait, which `hold_for` gives as `Hold::Retry` or `Hold::LimitReached` before the site's wait and the hourly limit. Per item, not per site: a MEGA limit is per connection, but each of its downloads finds out in one request. `try_now` (the `try_download_now` command) drops an item's own wait, or ends its site's "too many requests" wait (`SiteLimits::end`, keeping the count), and refuses the hourly limit, which is the user's own. Where what an archive holds goes is `UnpackPlace` (`UnpackSettings.place`, `#[serde(default)]` `Smart`, so settings from before keep what they did): `files::put_beside` puts `Smart`'s one thing as it is and several in a folder named after the archive, `ArchiveFolder` always in that folder, `InPlace` each thing as it is beside the archive (folders first, then files, by name; moved back into the work folder if one can't be moved), every name free (" (2)"). Archives are found by name only (`unpack::sets_among`), their parts in their folder, so a set whose parts come from several downloads is unpacked by the one that brings the last (`unpack::claim` keeps two from both doing it). Readers: the `zip` crate (`unpack/zips.rs`), `sevenz-rust2` (`unpack/sevenz.rs`; pieces `.7z.001` and `.zip.001` read through `unpack/joined.rs`), and RARLAB's UnRAR through `unrar_sys` (`unpack/rar.rs`, raw FFI with its callback, one at a time, wide names on Windows): UnRAR's licence lets it read rar archives but not be used to make a rar archiver, and its paragraph is quoted in README; it builds from C++ with MSVC here. Every reader writes through `files::Output` (`safe_relative` names, cancel, progress), into `<temp folder>\unpacking`, then `put_beside`. A run that couldn't unpack everything ends as `JobOutcome::NotUnpacked`; `finish` keeps its files in `QueueItem.unpack_files` (memory only) and Retry or Resume sends them as `JobSpec.unpack_only`, which skips downloading while the archives are all there. `DownloadError::Unpack` carries `UnpackProblem`; `FailureFixes`' `archivePassword` asks for the archive's password and retries with it (`enter_archive_password`). `UnpackSettings::normalized_passwords` (in `set_options`) drops blank lines and repeats but keeps spaces, which can be part of a password. Rar archives can't be made without WinRAR, so its tests use real ones from rarfile and unrar.rs (`tests/fixtures/archives/README.md`, licences there); `.gitattributes` marks them binary. `unpack_live` (ignored; `UNPACK_LIVE=<folder> UNPACK_PASSWORDS=<one per line> cargo test -p tsundoku-core --lib unpack_live -- --ignored --nocapture`) unpacks the archives in a folder beside them and prints what came of each, for archives made by 7-Zip or WinRAR.
- `DownloadSettings` (`settings.json` → `downloads`) is also what the UI edits: the download folder, downloads at once (1–5), the speed limit (checked and written as yt-dlp takes it, such as "900K"), the cookies browser and each paced site's pace (Settings → Pacing, one line per site: `sites::paced_site` names Instagram, X, Pixiv and Tumblr, and `DownloadSettings.pacing` (`SitePacing`) gives each a `SitePace`: `at_once`, 1 to `MAX_AT_ONCE`, one to start with, and `pause`, a `PauseRange` of at most 600 s, 3 to 5 s for Instagram and 0 to 2 for the others to start with, 0 to 0 for none). `DownloadSettings::pause_for` gives the pause (none when it's 0 s) to a post's gallery-dl run (`--sleep`, before each file, the first included) and to Pending's reader. `schedule` lets a download from a paced site start while fewer of that site's downloads, posts or videos, run than its `at_once`; each run pauses on its own, so each of the site's slots has its own pause. Settings saved before 0.1.147 had `postPause` (Instagram) and `sitePauses` (the others, `null` for none): `Settings::from_json` carries them over (`SitePacing::carried_over`) while `pacing` is missing, Instagram's 5 to 10 s (its old start) and a site's `null` taking the new start. The cookies browser applies to previews too, since a video that needs a signed-in account can't be previewed without it.

- **Click'n'Load** (`core::click_n_load`, `src-tauri/src/click_n_load.rs`, Settings → Adding Links → Take Links from Click'n'Load Buttons: `AddingSettings.click_n_load`, false by default and in settings from before; built at Fuzen's ask, with the recommended default while his choices on Open Decisions wait): the way a protected link folder hands its links to a download manager on the same PC once the person passed its check in their own browser. Tsundoku answers as JDownloader does (Click'n'Load 2, from JDownloader's wiki and pyLoad's receiver; JDownloader's GPL code read for the protocol only) on `http://127.0.0.1:9666` (`PORT`): `GET /jdcheck.js` answers `jdownloader=true;` and `var version='42707';` as JavaScript, `GET /flash/` (or `/flash`) `JDownloader`, `POST /flash/addcrypted2` takes a form's `crypted` (base64; a space stands for a plus, line breaks are dropped; at most 1 MiB) and `jk` (a JavaScript function returning 32 hex characters), `POST /flash/add` plain links in `urls`, and `POST /flash/addcrypted` (a DLC container, whose keys are JDownloader's own) is refused with 400; a post that worked answers `success`. **Decoding** (`decode`): the key is read from `jk`'s text as the quoted value it returns (`RETURNED_KEY`: `return '…'` or `return("…")`, then `;` or `}`); a function that computes it any other way is `DecodeError::KeyUnreadable`, since a page's script is never run. AES-128-CBC with the key as IV (`crate::cbc`, shared with MEGA's names), trailing zero bytes or a valid PKCS #7 pad removed, then only words starting with http:// or https:// are taken (`web_links_in`, through the watcher's `has_web_scheme`; NUL bytes part words), since decrypted garbage can look like a domain; with no link, the first block is tried as the IV once. The known-answer vectors in `decode`'s tests were made with .NET's AES. **The receiver** (`server`, hand-written on `std::net`): 127.0.0.1, and [::1] when it binds, never another interface; one request per connection, a head of at most 16 KiB (431), a body of at most 2 MiB (413), a Content-Length or none (a chunked body is 411), 10 seconds, at most 8 connections at once, `Server: Tsundoku/<version>`, `Connection: close`; a header value with a line break is never written. Dropping the `Receiver` stops it and frees the port before it returns. **Guards** (`answer`): the Host header must be `127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>`, else 403, so a site whose name resolves to this PC can't reach it. The sender is the Origin's host when it's there and not `null`, else the Referer's, else, for a post, its `source` field's (unverified). A post is taken only from `SENDERS` (a name and its domains, `sites::on_domain`), else 403 with a plain sentence and `ClickNLoadListener::refused`, which the app crate writes to its output (`Click'n'Load: refused links from <host>`); `/jdcheck.js` and `/flash/` are refused only when an Origin or Referer names an unlisted site. A listed Origin gets `Access-Control-Allow-Origin` echoed with `Vary: Origin`; its `OPTIONS` gets 204, `GET, POST, OPTIONS`, the asked headers and `Access-Control-Allow-Private-Network: true`. A multipart form is refused with 400. **Senders**: a site is listed once a real click of its button sent links here. FileCrypt (filecrypt.cc, .co, .to) is listed from its documented form, its real click pending (TESTING 71): its button calls `CNLPOP(id, key, crypted, name)`, and its script (`static.filecrypt.to/js/container/cnl.js`, read once as Tsundoku on 2026-11-12) opens its own `http://<its domain>/helper.html` in a pop-up and hands it the key and the links by `postMessage`; that page makes the post (not read), so the sender is FileCrypt's own address, over plain http. **The links** go to Pending through `PendingLinks::add_from_page` (`LinkOrigin::Page`, 3 in `pending_links.caught`, which a version from before 0.1.129 reads as copied), kept as links from a dropped file are (Fuzen's "Keep it as is"): read with the generic extractor off, gone without a word when nothing can download them, marked when downloaded before, never announced one by one, and never started by themselves, whatever Download Right Away or a rule says, since a sender can't always be told for sure. `PendingLink.from_page` hides them until read, counted apart ("Checking 12 links pages sent…"). Short links and mirror pages among them resolve as usual. `background::page_sent` gives one notification through `announce` (Show Notifications): "FileCrypt Sent 12 Links", "They're being read in Pending." The form's `passwords` field is ignored. **The app** (`click_n_load::apply`): at launch when the setting is on, and whenever `save_adding_options` saves (on again after the port was taken is Settings' Try Again); `click_n_load_status` and the `click-n-load-changed` event carry `ClickNLoadStatus` (`ReceiverState`: `off`, `listening`, `portTaken` when the bind says `AddrInUse`, `failed`; the port; `Senders::names`), which Settings' line shows. It runs as long as the app, in the tray too. Development builds read `TSUNDOKU_CNL_TEST_SENDER=<host>` (a test page's host counted as the sender "Test Page") and `TSUNDOKU_CNL_TEST_PORT=<port>` (so a test copy runs beside a JDownloader that has 9666, and a test page never sends it anything); release builds read neither. In a browser, `?portTaken` shows the port-taken line. **What the browsers did** (2026-11-12, a test page of Claude's own served from 127.0.0.1:8123, the receiver on 9670): Chrome 157, Edge 157, Playwright's Chromium 148 and Firefox 159 (headless) took the probe, a form into a hidden frame and a fetch, page and receiver both on this PC. With the page counted as public (`--ip-address-space-overrides=127.0.0.1:8123=public` in Chrome, `network.lna.address_space.public.override` in Firefox): Chrome blocked all three (`ERR_BLOCKED_BY_LOCAL_NETWORK_ACCESS_CHECKS`, "Permission was denied… `loopback`") until the `local-network-access` permission was granted, then took them; from a public page over plain http, which isn't a secure context (as FileCrypt's helper), Chrome blocked them outright ("The request client is not a secure context") and the permission couldn't be granted, but a form posted into a new window (a top-level navigation) got through. Firefox 159 failed the probe and sent neither the frame's form nor the fetch (headless, so any question it asks couldn't show), while the new window's form got through. Fuzen's own JDownloader was running on 9666 (127.0.0.1 and [::1]): the test copy said the port was taken, and JDownloader was left alone.
