## Introduction

- Tsundoku is a Windows desktop app (Tauri 2: a React + TypeScript UI over a Rust core) that downloads videos with yt-dlp and keeps a history of everything it has downloaded, so it can warn before a duplicate.
- [PROJECT.md](./PROJECT.md) holds the original spec and its decisions, [TODO.md](./TODO.md) the features planned after v1.

## Rules

- All UI text lives in `tsundoku/src/strings.ts`, in English. Never write UI text in a component.
- UI labels use Title Case: buttons, toggles, navigation, headings, dialog titles and buttons, placeholders, column headers and short names. Minor words (a, an, the, and, or, of, to, in, on, for, with, as, at, by, from) stay lowercase unless first or last, and hyphenated words take both capitals. Sentences (descriptions, messages, empty-state explanations, status texts) stay in sentence case. See [DESIGN](./DESIGN.md).
- `tsundoku-core` (`tsundoku/core`) has no Tauri dependency. Downloads, the history, the tools, presets and settings go there, with unit tests; the app crate (`tsundoku/src-tauri`) only exposes them as commands and events, and the UI only presents.
- Types the UI reads are Rust types in the core deriving `ts_rs::TS` with `#[ts(export)]`; `cargo test` writes them to `tsundoku/src/bindings`. Never hand-write a TypeScript type that mirrors a Rust one, and commit the regenerated files with the change.
- `tsundoku/src/api.ts` is the only place that calls `invoke` or another Tauri API.
- Before a visual change, read [DESIGN](./DESIGN.md). If something differs notably from it, tell the user.
- Never suppress, ignore or work around an ESLint, Clippy or TypeScript error or warning; fix the cause.
- Meta files (docs, scripts) go at the project root; `tsundoku/` holds code only.
- After implementing a feature, update [FEATURES](./FEATURES.md) and remove the item from [TODO](./TODO.md) if it is listed.
- A change the checks can't confirm on their own (how it looks or behaves in the real app, a real site's answer) gets an entry in [TESTING](./TESTING.md) in the same commit: its version, where in the app, what to do and what should happen, and whether it was tried in the real app. Entries leave once the user confirms them.
- A question only the user can answer (an approval, a choice between two behaviours, whether to start something) goes on the [Open Decisions](https://claude.ai/artifact/A8Ewo1fPXDbs7CP6hgzwFj) page rather than waiting in a thread: add a document to its `decisions` collection with the ArtifactData tool (`title`, `group`, `order`, `context`, `source`, `options` as `{id, label, detail}`, `recommended` or `defaultOption`, `status: "open"`, `addedAt`), and meanwhile build the recommended answer where it is easy to change later. The user's answers are in its `answers` collection (`choice`, `choiceLabel`, `text`); the thread that acts on one sets the decision's `status` to `"done"` with a one-line `resolution`.
- Every change bumps the patch version and gets an entry in [CHANGELOG](./CHANGELOG.md); a commit that bumps the version is tagged `vX.Y.Z`. A release bumps the minor or major version and folds in the patch entries since the previous release.

## Technical Notes

- The main window starts hidden and transparent (`tauri.conf.json`). `src-tauri/src/lib.rs` applies Mica, which needs Windows 11, and records whether it worked. `main.tsx` reads that through the `app_info` command before the first render and sets `data-backdrop` on `<html>`: `mica` makes the page transparent, `solid` paints `--color-bg`. `App` shows the window after its first frame, and Rust shows it anyway after 3 seconds if the UI never does.
- **Theme** (Settings → Appearance: `settings.appearance`, `appearance_options` and `save_appearance_options` in `src-tauri/src/appearance.rs`): `Theme::Auto`, `Light` or `Dark`. `appearance::apply_theme` calls the window's `set_theme` (`None` for Auto) in `setup`, while the window is still hidden, and again when the choice is saved. On Windows that sets the title bar's dark mode, which Mica's tint follows, and tao's `ThemeChanged` then makes tauri-runtime-wry set WebView2's preferred color scheme. The UI doesn't rely on that: `main.tsx` reads the options (`appearance_options`) with `app_info` before the first render and `theme.ts` sets `data-theme` on `<html>`, from which `index.css` sets `color-scheme` (`light`, `dark`, or `light dark` for Auto), so every `light-dark()` token follows. Choosing a theme sets `data-theme` at once, and back if saving fails. The accent (`AppearanceSettings.accent`, `Accent`) is the UI's alone: `applyAppearance` sets `data-accent` on `<html>` beside `data-theme`, and `index.css`'s `[data-accent="…"]` blocks override the four accent tokens, on any element, so the picker's swatches show their own. Custom (`AppearanceSettings.custom_accent`, `#rrggbb`, checked by `AppearanceSettings::checked` when saved) is set as `--accent-custom` on `<html>` whatever the accent, and its block derives the four tokens with relative OKLCH colors; the swatch opens Windows' color picker through `pick_color` (`appearance.rs`, `ChooseColorW` on a blocking thread, owned by the window, its 16 custom colors kept while the app runs), since WebView2 opens nothing for a color input; in a browser, `pickColor` clicks a temporary color input instead.
- `single-instance` is the first plugin registered, as it requires: a second launch focuses the running window. `window-state` restores size, position and maximized state, never visibility.
- Every Tauri permission the UI uses is listed in `src-tauri/capabilities/default.json`; `core:window:allow-show` is there for the hidden start.
- The CSP in `tauri.conf.json` allows `https:` images, for video thumbnails. Network requests (GitHub) come from Rust, never from the UI.

### Releases

- A release is a version tag pushed to GitHub: `.github/workflows/release.yml` checks that the tag matches `package.json` and `Cargo.toml`, runs `Scripts\Check.cmd`, checks the committed bindings are current, then `tauri-action` builds the installer, signs it and publishes a release with `latest.json` for the updater, and a last step sets `.github/release-notes.md` as the release's text (`tauri-action` only takes it as a string). Before the build, "Read this version's changes" takes the version's CHANGELOG section (from its `## <version>` heading to the next `## `) as `tauri-action`'s `releaseBody`, which becomes `latest.json`'s `notes`, the update's `body` in the updater and the banner's What's New; the step after replaces only the release page's text. A version without a section warns and leaves the notes empty. Running the workflow by hand builds without publishing or signing, and keeps the installer with the run: a way to test a build before tagging.
- Push the tag on its own, after the commit (`git push origin main`, then `git push origin vX.Y.Z`). The v0.1.0 tag, pushed in one go with the commit that first added the workflow, started no run.
- A run takes about 20 minutes without a cache and 10 with one.
- Releases aren't marked pre-release, even for 0.x: the updater reads `releases/latest/download/latest.json`, and GitHub's "latest" skips pre-releases.
- Signing: the private key and its password are the repository's `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` secrets; the user keeps the key file outside the repository. Only the public key is in `tauri.conf.json` (`plugins.updater.pubkey`). Losing the private key means installed copies can't update anymore: a new key needs a new install.
- `src-tauri/tauri.release.conf.json` turns on the updater's files (`createUpdaterArtifacts`) for the release build only, since making them needs the private key. `Scripts\Build.cmd` builds the installer without them.
- `requireSignedVersion` is on: the updater refuses a release whose signature names another version, so an older signed release can't be served as a newer one.
- The installer is NSIS, per-user (`installMode: currentUser`), into `%LocalAppData%\Tsundoku`. Updates install in passive mode: a progress bar, no questions.
- While the repository is private, the update check fails (GitHub won't serve its release files without signing in) and the app shows nothing; Settings → About shows the error.

### Portable Copies

- A release build whose exe has `.portable.txt` beside it (`data_folder::PORTABLE_MARKER`) is portable. `make_portable_if_marked` in `src-tauri/src/lib.rs` checks before Tauri starts and sets `app.appDirectoriesOverride` (Tauri 2.12) on the context's config to the `data` folder beside the exe, so every app folder follows: `app_local_data_dir` (the data folder, which `data_folder::resolve` takes for a release build), `app_config_dir` (window-state's file) and the WebView's `EBWebView`. Development builds ignore the marker.
- `data_folder::set_portable_folder` records the copy's folder for the core (`data_folder::portable_folder`): a download folder that isn't a full path is inside it (`settings::BESIDE_APP_DOWNLOADS`, "Downloads", chosen at setup), so it follows the copy to another drive. `AppInfo.portable` tells the UI.
- A portable copy doesn't check for updates (`useAppUpdate` is off): Tauri's updater only runs the NSIS installer, which would install Tsundoku instead of replacing the copy. Replacing the exe in place (a `windows-x86_64-portable` entry in `latest.json`, signed with `version:` in its trusted comment since `requireSignedVersion` is on) and a zip in the release run are for a public portable release, with registering the notification ID (`HKCU\Software\Classes\AppUserModelId\<identifier>`, which the installer's shortcut does otherwise) and re-pointing Start with Windows when the folder moves (`enable()` also re-approves the entry in Task Manager, so only when the path changed).
- `background::startup_name` makes Start with Windows "Tsundoku (Portable)", apart from an installed copy's "Tsundoku". Both copies share the single-instance lock (the identifier), so only one runs at a time, and the browser bookmark's `tsundoku://` follows whichever started last.

### First-Run Choices

- `first_run::options` and `save` (the `first_run_options` and `save_first_run_choices` commands): where the tools go (`ToolsSettings.folder`, `None` for the data folder's `tools\`), their caches (`ToolsSettings.caches`) and the download folder. They're `needed` while `tools.caches` is `None` and yt-dlp or ffmpeg isn't set up, so an install from before 0.1.20 is never asked. The UI's `SetupView` shows `ChoicesScreen` first, then `ToolsScreen`; saving sets `needed` to false in the query, and Back sets it to true.
- `ToolManager::tools_folder` is the chosen folder or the data folder's `tools\`, for installs, updates, finding Tsundoku's copies and running them.
- A portable copy is also offered an installed copy's `tools\` in AppData (`FirstRunOptions.installed_tools_folder`: Tauri's `local_data_dir`, which the override leaves alone, joined to the identifier), picked when `tools::has_own_copies` finds Tsundoku's copies there. The tools screen's detection then finds them as Tsundoku's own (`locate::candidates` looks in the tools folder first), and Use This Copy sets them up as managed with no stored checksum.
- `ToolCaches::DataFolder` gives runs a `ToolCacheFolder` (`ToolManager::cache_folder`) for the data folder's `cache\`: yt-dlp gets `--cache-dir cache\yt-dlp` and its Deno `DENO_DIR=cache\deno` (`ProgramCommand::variable`, inherited by the Deno yt-dlp starts), gallery-dl `-o cache.file=cache\gallery-dl\cache.sqlite3`, whose folder Tsundoku makes since gallery-dl silently keeps its cache in memory otherwise. `UsualFolders` or `None` passes nothing. Previews (`FetchTools`, `GalleryTools`) and downloads (`JobSpec`) both get it.

### Backups

- Settings → About's Back Up and Restore (`views/settings/BackupRow.tsx`) call `save_backup` and `restore_backup` (`src-tauri/src/backup.rs`), which run `core::backup::create` and `restore`. A backup is a zip: `manifest.json` (`format`, `appVersion`, `schemaVersion`, `createdAt`), `settings.json` without `tools`, `tsundoku.db` and `archive.txt`.
- The database is copied with `VACUUM INTO` on the open connection, so the copy is consistent while downloads run; the copy then loses `queue_items` and `pending_links` and is switched to `journal_mode=DELETE`, so it's one file. The app crate manages the `Arc<Database>` for this.
- A restore reads and checks everything before changing anything, in a working folder under the data folder's `backups\`: a `format` or `appVersion` newer than this one, or a database `Database::open` refuses, is `NewerVersion`; opening the database also migrates an older one. It then saves the current data there as "Tsundoku Backup <local date and time> (Before Restore).zip", replaces the settings (keeping this PC's `tools` and `background.startWithWindows`, whose Windows entry is only changed when saved, and dropping a download folder that isn't a full path unless the copy is portable), then the history's rows in one transaction through `ATTACH` (`SELECT *` works because both databases went through the same migrations), putting the settings back if that fails. Finished queue items are deleted, since their `result.downloadId` names a download in the replaced history. The UI restarts the app (`relaunch`) afterwards, so the shortcut, the tray, the theme and every query read what was restored.

### Copy Details

- A failed queue row's Copy Details (`components/CopyDetailsButton.tsx`) calls `download_details` (`src-tauri/src/report.rs`) with the error as the row shows it (`ShownError`), and copies the answer with `copyText`. The command puts a `core::bug_report::DownloadReport` together: the app's version, `system::windows_version` (the registry's `ProductName`, `DisplayVersion`, `CurrentBuild` and `UBR`, with "Windows 10" read as 11 from build 22000), each tool's version from `ToolManager::overview` (which runs them, so it takes a moment), the video's `url` and `bug_report::log_tail` (the last 50 lines, from the log's last 64 KiB).
- `UserNames::blank` replaces the user's folder (`dirs::home_dir`) with `<user>` for its name, with backslashes, slashes or JSON's doubled backslashes, ignoring case, then the folder's name and `USERNAME` as words of their own (no letter or digit beside them). A name under three letters is only blanked in the folder's path.

### What's New

- **After an update**: `src-tauri/src/whats_new.rs` embeds the root's CHANGELOG.md (`include_str!`) and answers `whats_new` with `core::changelog::whats_new`: the sections newer than `settings.lastRunVersion`, up to the running version, newest first (`changelog::sections` splits the file at `## <version>` headings, " · <date>" optional). With nothing to show, the running version is recorded at once; otherwise once the card is closed (`dismiss_whats_new`), so a start in the tray doesn't lose it. `note_start`, in `setup`, records the version at once on a first install (`ToolManager::needs_setup`), so its setup ends with nothing to tell; an install from before `lastRunVersion` existed shows only the running version's section. A restored backup keeps this PC's `lastRunVersion`. The UI's `WhatsNewCard` reads it once (`useWhatsNew`) and `ReleaseNotes` (`notes.ts`) shows the Markdown: headings, `- ` lists, paragraphs, bold, code and http(s) links, opened with `openWebPage`.
- **Before an update**: `AppUpdate.notes` is the updater's `body` (see Releases), shown by the update banner's What's New toggle; when it's empty, `releasePage` (the release's tag on GitHub) is linked instead. In a browser, `?update` shows the banner with stand-in notes, `?update=bare` without, and `?whatsnew` the card.

### Running Programs

- `core::process` is the only place that starts yt-dlp, ffmpeg, Deno or gallery-dl. Each starts without a console window (`CREATE_NO_WINDOW`), suspended, is put in a new job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, then resumed, so it can't start anything outside the job. Ending the job ends yt-dlp and the ffmpeg it started; closing the job's handle (when the app exits or crashes) does the same.
- process-wrap was tried and dropped: its job object for `std` never sets kill-on-close, so the tools would outlive a crash.
- Every run is counted from just before it starts until it and everything it started have ended (`RUNNING_PROGRAMS`). Windows lets a folder be renamed while a program in it runs, so an install can't rely on the swap failing: `unless_running_from` does the swap only while no program runs from the tool's folder, and no program starts until it's done.
- Output is read line by line on two threads into a channel; a carriage return also ends a line. `run` polls every 100 ms for cancellation and its time limit.
- Tauri commands that run programs or download are `async` and do the work through `spawn_blocking`, since a sync command runs on the main thread and would freeze the window.

### Tools

- `core::tools::catalog` names each tool's release host, repository, release file and checksum file. gallery-dl (`mikf/gallery-dl`, the standalone `gallery-dl.exe`) comes from **Codeberg**, where its development moved in 2026: its GitHub releases since 1.32 have no files. Codeberg runs Forgejo, whose `/api/v1/repos/<repo>/releases/latest` answers in the same shape as GitHub's (`tag_name`, `published_at`, `assets` with `name`, `size` and `browser_download_url`), so `github.rs` reads both; its `SHA256SUMS` uses the `<hash>  <name>` form. Since 0.1.25 the first-run setup sets it up with the others (`ToolId::SETUP` is every tool, `setupToolOrder` in the UI), but like Deno it's optional: the setup can be left when only optional tools failed (`optionalTools`), and `needs_setup` asks only for yt-dlp and ffmpeg, so an install from before isn't sent back to it. It's run with `--config-ignore`, gallery-dl's spelling of yt-dlp's `--ignore-config`. ffmpeg comes from yt-dlp/FFmpeg-Builds' **shared** build (91 MB, 193 MB installed), not the static one (202 MB, 340 MB installed): ffmpeg and ffprobe share their DLLs instead of each carrying a copy. Everything in its `bin` folder is kept except ffplay.
- Checksum files come in two forms: `<hash>  <name>` lines (yt-dlp, FFmpeg-Builds) and PowerShell's `Hash : <HASH>` (Deno's `.sha256sum`). `checksum.rs` reads both.
- An install downloads to `tools\.download-<tool>\`, checks the SHA-256, unpacks to `tools\.new-<tool>\`, then swaps that folder in for `tools\<tool>\` (the old one moved aside, deleted after, put back on failure) once no preview, read or download runs the old copy: it waits up to 5 minutes (`ToolStage::Waiting`), then gives up with `ToolError::InUse`. Each tool has its own working folders, since the setup installs all three at once. Afterwards the tool is run (`--version`) to catch an antivirus quarantine.
- GitHub allows 60 API requests an hour per network without signing in. The latest release of each tool is cached for 10 minutes, so the setup's sizes and downloads cost one request per tool.
- yt-dlp updates itself with `--update-to stable@latest` (or `nightly@latest`). Naming the release, not just the channel, lets it go back from a nightly build to an older stable one, which plain `--update-to stable` refuses as a downgrade. It renames itself to `yt-dlp.exe.old` while updating and deletes that at its next update.
- yt-dlp and gallery-dl update themselves once a day (`ToolId::UPDATED_DAILY`): `tools::start_daily_updates` in the app crate runs `ToolManager::run_due_updates` at startup and every 10 minutes after, so a copy left in the tray for days is updated too. A tool whose last check (`ytDlpLastUpdateCheck`, `galleryDlLastUpdateCheck`) is a day old is updated, unless a program from its copy is running, which leaves it for a later look. The check is recorded even when the update failed, so a failing update isn't retried at every start, but not when it gave up because the old copy stayed in use. gallery-dl updates through the app's own install (`update_gallery_dl`, also Settings' Update Now), only when the latest release's SHA-256 differs from its copy's: its own `--update` looks for GitHub releases, which have had no files since it moved to Codeberg.
- Settings → Tools' Update All (`update_all_tools`, `ToolManager::update_all`) runs each managed tool's update in turn, yt-dlp through `update_yt_dlp` and the others through `update_to_latest`, and answers a `ToolUpdateOutcome` for each (`updated`, `upToDate`, `failed`), skipping the user's own copies; a failure doesn't stop the rest. The cards follow through `tool-progress`, and a card forgets a found update once its copy's version changes.
- ffmpeg, Deno and gallery-dl are compared by the SHA-256 of the release file they came from, stored in `settings.json`. FFmpeg-Builds rebuilds daily under the rolling tag `latest`, so its releases are labelled by date. A copy adopted from `tools\` at setup has no stored checksum, so its first check always offers an update.
- Progress reaches the UI as `tool-progress` events (`ToolProgress`); every install or update ends with one whose stage is `null`. `tools-changed` tells the UI a tool changed on its own (the daily update of yt-dlp or gallery-dl).
- A tool's errors reach the UI as `ToolError`, a tagged union; `errors.ts` turns each kind into a sentence from `strings.ts`, with the technical `detail` underneath. `PreviewError` and `HistoryError` work the same way.

### Metadata and Preview

- `metadata::normalize_link` accepts only http and https links with a host (adding `https://` when there's no scheme), so pasted text, a search (`ytsearch:`) or a file path never reaches yt-dlp. The link is also passed after `--`, so nothing in it can be read as an option.
- yt-dlp runs as `--ignore-config --no-playlist --flat-playlist --dump-single-json --encoding utf-8`, with `--js-runtimes deno:<path>` when Deno is set up (`--no-js-runtimes` otherwise, so a Deno on PATH can't hide that it's missing) and `--ffmpeg-location`. `--flat-playlist` makes a playlist or channel answer at once instead of reading each video; `--encoding utf-8` keeps its messages from being mangled by the Windows code page. The Deno path must be a Windows path: yt-dlp silently ignores a `/d/…` one.
- The site is yt-dlp's `extractor_key` in lowercase, as yt-dlp's archive writes it (`youtube`, `soundcloud`, `archiveorg`), and with the video ID it's what the duplicate check matches on. A format counts as video when it has a height and isn't `vcodec: none`, since some sites (archive.org) give no codec.
- yt-dlp reports a failure as its last `ERROR:` line; `classify_failure` sorts it into a `PreviewError` by phrases in it. Upcoming premieres are errors too ("This live event will begin in…"), not a field of the answer. When a site's message changes, add the new phrase and a test.
- **Two tools read links.** `sites::prefers_images` sends image sites (Instagram, X, Bluesky, Pixiv, Tumblr, boorus…) to gallery-dl first and everything else to yt-dlp; `preview::read_link` then falls back to the other tool when the first answers "unsupported" or yt-dlp finds no video (`PreviewError::NoVideo`), or when gallery-dl fails to read a site it knows. A missing sign-in or an unavailable post isn't retried. Without gallery-dl, a photo post is `ImagesNotSetUp`, which the UI offers to fix. The user is never told which tool read a link (the user's choice: tools are internals), so preview errors don't name yt-dlp.
- `gallery::fetch` runs `gallery-dl --config-ignore --dump-json -- <link>`. Its answer is a list of messages: `[2, post]`, `[3, url, file]` per file, `[6, url, …]` for a link elsewhere (a profile's posts), and `[-1, {error, message}]` for a failure, which still exits 0. `sort_answer` groups the files under their post (a `[2]` naming the same post again doesn't start another); an answer of several posts, or of links elsewhere only, is a page that can't be read as one post and is refused as `NotListable`. Only an unsupported link exits non-zero (64). Signed out, Instagram redirects to its login page and X refuses media timelines, so both need cookies even for public posts. Instagram's API may instead answer with a `KeyError` about a field ending in `_connection` (`'xdt_api__v1__…_connection'`), which only a signed-in answer has: `classify_message` sorts it as a sign-in (`missing_signed_in_field`), not as the dropped connection its word suggests, so it's never retried by itself, and no other `KeyError` counts as a network error either (they're site errors).
- **Files that are neither images nor videos** (a .zip or .pdf on Pixeldrain, Gofile, Bunkr or Cyberdrop, which gallery-dl reads as a post of one file): `gallery::kind_of` sorts each file by its extension (`VIDEO_EXTENSIONS`, `IMAGE_EXTENSIONS`), then its `mime_type`; one without an extension stays an image. Others count in `PostContents.others` (`#[serde(default)]`, so posts saved before read as 0), shown as "1 file", get no thumbnail (their address is the file itself, which the card would fetch whole), and a post of one such file with no caption or uploader is titled by its `name` (`lone_file_name`). The history keeps only `post_images` and `post_videos`, so such a download shows no contents there. A Pixeldrain .zip was read and downloaded in the dev app (2026-11-11); Gofile, Bunkr, Cyberdrop and Pixeldrain's lists weren't tried.
- A post becomes a `VideoInfo` with `post: Some(PostContents)`. Its key is gallery-dl's category and the post's ID (`post_shortcode` on Instagram, `tweet_id` on X), the same as yt-dlp's archive gives for those sites, so a reel downloaded with either tool is one history entry.
- **Picking a post's files**: `gallery::post_files` gives `VideoInfo.post_files`, a `PostFile` per file: `number` from 1 in the `-j` answer's order, `video`, `thumbnail_url` (`display_url`, which Instagram gives its videos as their cover, else the image itself, X's asked at `name=small`; none for an X video) and `picked`. The pick rides on the video: a file left out has `picked` false, so a queue item's and a pending link's JSON keep it with no column of their own. `VideoInfo::picked_post_files` becomes gallery-dl's `--range 1,3,6` (`PostJob.range`; on 1.32.19 a list works, counting the files in the `-j` answer's order, and `num` stays each file's place in the post, so the names keep it) and `post_file_count` the progress's count. `DownloadQueue::add_post` refuses a post with every file unticked (`DownloadError::NothingPicked`). `History::record` numbers each file of a post in `download_files.post_number` (migration 9) by the picked files' order, leaving them NULL when the counts differ; `History::left_out_files` (the `left_out_files` command, `useLeftOutFiles`) gives the post's files no download took, `None` when one took it whole or was made before numbers were kept. The preview card ticks those to start with (`postFiles.ts`: `defaultPick`, `withPicked`); a pending link's ticks are set from them when it's read (`PendingLinks::read`), and `set_post_files` (`set_pending_post_files`) saves new ones. `post_files` isn't serialized when empty, so it's optional in TypeScript.
- **Posts' file names** (Settings → Posts of Images: `settings.downloads.postFileName`, `post_names`): "{account} {date} {post} {number}" to start with. `post_names::check`, through `DownloadQueue::set_options`, refuses a name without `{post}` and `{number}` (two files could get one name, and gallery-dl would skip the second as already there), with an unknown `{word}` or with a character Windows refuses, and takes a blank one as the default. `gallery_format` turns it into gallery-dl's `--filename` for each post, in `job_for`: the post's ID, date and site (`rules::site_name`, as `{site}` gives it) as text from the preview, braces doubled; the account as gallery-dl's field for the site (`username` on Instagram, `author[name]` on X, a list of the usual ones elsewhere) with the uploader, or else the site, as a quoted fallback (`{username|'natgeo'}`), since a field missing or empty prints "None"; the number as `{num|filename}`; then `.{extension}`, which gallery-dl doesn't add to a `-f` of its own. A placeholder without a value (a post without a date) goes with the text before it, or after it when it's the first. gallery-dl turns characters Windows refuses in what the site gives into `_`. The UI's example fills the placeholders with samples (`fillPlaceholders`).
- Pixiv needs a gallery-dl OAuth refresh token (`gallery-dl oauth:pixiv`), not browser cookies, so it fails with a sign-in error for now.
- gallery-dl's Windows build bundles yt-dlp, for the `ytdl:` URLs some extractors (Instagram's DASH videos) use.
- `PreviewService` runs one fetch at a time: starting one cancels the one before, and the UI ignores an answer that arrives after a newer request (`usePreview`).
- **Channels, playlists and accounts** (`core::listing`, the UI's `components/ListingPicker.tsx` and `listingPicker.ts`; [Download Pipeline](./DOCUMENTATION/Docs/Download%20Pipeline.md#from-a-channel-playlist-or-account)): `fetch_preview` answers a `LinkPreview`, either `video` (a `VideoPreview`) or `listing` (a `Listing`: `kind` (`ListingKind`: `channel`, `playlist`, `account`), `title`, `uploader` (a playlist's owner), `site_name`, `url`, `thumbnail_url`, `total`, `newest_only` and `items`, each a `ListedItem` with `video`, `approximate_date`, `last_download` and `in_queue`). `listing_link` decides from the address alone, which `listing_kind` also tells the UI for its waiting text: YouTube `/@name`, `/channel/`, `/c/` and `/user/` with any tab become `/…/videos` (newest 50, `--playlist-end`), `/playlist?list=` is listed whole, `watch?v=…&list=…` stays one video; Instagram `/name/`, `/name/posts/` and `/name/reels/` become `/name/posts/` (newest 50, `--post-range`, sorted by date since pinned posts come first). `read_any` reads any other link with yt-dlp and lists another site's playlist when every entry has a page, an `ie_key` and an `id` of its own and none is a listing (`is_listing_extractor`); a video listed twice is kept once, two items on one page refuse it. Entries are keyed as their own link would be, upcoming and live ones are left out, and a channel's videos get the channel as their uploader and its handle as their `account`. Every item gets the listing's title as its `playlist` (`name_items`), which `{playlist}` puts in a rule's folder; a link added on its own has none. YouTube's flat dates are rough (`approximate_date`, shown as "3 weeks ago" by `formatRoughAge`), so `upload_date` stays empty for them. Download Selected sends `QueuePick`s to `add_many_to_queue` (`DownloadQueue::add_many`: `insert_video` and `insert_post` for each, one `schedule` after), each video with the preset a rule picks (`useRulePresets`) else Videos Start As. A pending link that's a listing is refused as `Playlist` before any tool runs (`read_with_tools`); copied ones leave quietly, as `NotListable` ones do. `listing::before_known_ground` is for checks of watched links: it stops past `PINNED_AT_MOST` (3) known items in a row, so pinned posts it knows don't end a check.
- **Watched sources** (`core::watched`, the Watched view, `views/WatchedView.tsx`, and `components/WatchForm.tsx` on the picker; phase 2 of [Watched Links: Design](https://claude.ai/artifact/BA3qCJoBKUG63GmAjbfZez)): `watched_sources` and `watched_items` (migration 12, `watched/store.rs`). A source keeps every item it has met with a state: `new` (on its card), `skipped` (Skipped Before), `queued` or `seen` (known without showing: downloaded or queued when it was added, or past what `FirstItems` asked for). Items are ordered by `position`, each find saved below the lowest, so the latest find comes first. `WatchedSources::add` takes the picker's `Listing` as `NewWatchedSource` with `FirstItems` (`fromNow`, `latest {count}`, `all`: Fuzen asked for the choice when adding); items the history or the queue has are `seen`. `check` queues the source for a thread of its own (`run_checks`, one at a time), which reads the listing through `ListingReader` (`preview::ToolReader`, `read_for_preview`, refusing anything that isn't a listing), keeps to `DownloadQueue::site_wait` and `slow_down` as the preview card does, and keeps as `new` what neither the source, the history nor the queue knows: `listing::before_known_ground` for a channel or an account, the whole list for a playlist. `download` queues the picked items through `add_many` with `QueuePick.folder` set to the source's Save In filled by `rules::filled_folder` (so it beats every rule, as a picked folder does) and the source's preset, else the rule's, else the default; with `skip_rest`, the other new items become `skipped`. `watched-changed` carries every source (`WatchedSource`, with `new_items`, `skipped_items` and `checking`); the UI also refetches on `queue-changed`. No schedule yet (phase 3). A backup copies the tables, but a restore only replaces the history's.
- `dragDropEnabled` is `false` in `tauri.conf.json`: with Tauri's own drop handling on, WebView2 never gives the page a dropped link.
- **Keyboard shortcuts** (`shortcuts.ts`): Ctrl+V outside a text field is the document's `paste` event, which Chromium fires at the focused element or the page even when nothing there is editable, with the text in `clipboardData`, so it needs no clipboard permission; `App` passes the text to the add bar's own `addText`. Ctrl+L, Ctrl+1 to Ctrl+7 (`SHORTCUT_VIEWS`, the sidebar's order) and Pending's Delete are `keydown` listeners that call `preventDefault`. Each takes Ctrl alone or no modifier, so none is a clipboard shortcut (`ClipboardShortcut`), and digits go by `code`, not `key`, for AZERTY keyboards.

### File Hosts

- MEGA, MediaFire, Google Drive, Dropbox, OneDrive, pCloud, WeTransfer, the Internet Archive, Yandex Disk, Box, Icedrive, 1fichier, SwissTransfer, Files.fm and upload.ee are read and downloaded by Tsundoku itself (`core::hosts`, `downloads::file_runner`), with no tool, through `reqwest`. `hosts::Host::of` picks them by domain before yt-dlp or gallery-dl is asked, in `PreviewService` and in `ToolRunner` (a job with `files` set). Like the tools, the host stays out of the UI's words, except as the site's name.
- **Adding a host**: each host's module holds its `FACTS` (`HostFacts`: name, history site, domains, whether it sends attachments, its `read`, and its `page_error` when its pages say more than their status), its file source type and its `address` when it has one. `Host` then needs the variant, a line in `ALL` and in `facts`, and `FileSource` a variant. Supported Sites, `{site}`, `sites::site_of` and the clipboard watcher follow `Host` by themselves.
- A host's reader turns a link into a `Share`: the file or folder's ID and name, and its files (`RemoteFile`: path inside the download's folder, size, `FileSource`). The preview sees it as a `VideoInfo` with `files: Some(FileContents)` (count and bytes, migration 4: `videos.file_count`, `file_bytes`). The download reads the link again, since download addresses expire, and asks each file's address just before fetching it.
- **MEGA**: the key is the part of the link after `#`, never logged. The API is `POST https://g.api.mega.co.nz/cs?id=<n>[&n=<folder>]` with a JSON list of commands: `{"a":"g","p":<file>}` (or `"n"` inside a folder) for a file's size, attributes and address (`"g"`, missing once the transfer quota is used up), `{"a":"f","c":1,"ca":1,"r":1}` for a folder's nodes. A file's 32-byte key XORs into the AES-128 key; bytes 16–24 are the counter's nonce and 24–32 the meta-MAC. Contents are AES-128-CTR (seekable, so a part file resumes), names AES-CBC with a zero IV (`MEGA{json}`), folder nodes' keys AES-ECB under the folder key. A node's `k` can hold several `handle:key` pairs separated by `/`, and the link's key opens only the one under the shared folder's own node (the folder whose parent isn't listed, `share_root`): that one is tried first, then the rest, and a node none of them opens is left out with what's inside it. The check is MEGA's chunked CBC-MAC (chunks of 128 KiB growing by 128 KiB to 1 MiB), folded to 8 bytes. Error -3 (busy) is retried with backoff, then is a network error like -18; -2/-9 (missing), -11 (access refused) and -16 (taken down) are Unavailable; -4/-6/-17 are LimitReached. Test vectors in `hosts/mega/tests.rs` come from async-mega-py (Apache-2.0); GPL code (megatools, gallery-dl) was read for the protocol only.
- **MediaFire**: `file/get_info.php`, `folder/get_info.php` and `folder/get_content.php` (API 1.4, `response_format=json`, files and folders separately, 1000 a chunk) list a share with sizes and SHA-256s. The address is the file page's Download button (`a#downloadButton`'s `href`, or its base64 `data-scrambled-url`); a page that answers with the file itself is used as it is. Some files' pages redirect to `?action=check`, which Cloudflare answers with 403 and its browser check; Tsundoku doesn't try to pass it (`check::is_browser_check` makes it `PreviewError::BrowserCheck`), and the download waits for the person (below). That address (`download<n>.mediafire.com/<token>/<key>/<name>`) is also taken as a link, since userscripts and download managers' add-ons copy it: `parse_link` reads the file by its key and keeps the link as `MediaFireFile.direct`, which `address` probes first (`hosts::probe`) and downloads from while it gives the file, asking the page only once its token has run out.
- **Checks only a person can pass** (`hosts/check.rs`, `downloads/holds.rs`, `src-tauri/src/check_window.rs`; Fuzen's answer on Open Decisions: show the check, and let it be skipped): Cloudflare's challenge, `cf-mitigated: challenge` or a 403/503 with `_cf_chl_opt` (`check::is_browser_check`, in `Host::page_error` for every host), is `PreviewError::BrowserCheck`. Tsundoku never tries to get past one: no disguised connection, no solving or scripting it, no copying its cookies into its own client. In `file_runner`, a file whose address or download meets one and whose host has a page a person can open (`CheckPage::of`: MediaFire's `/file/<key>`) is left for later while the others download, and the run ends as `JobOutcome::NeedsCheck` with a `BrowserCheck` (the site and those pages). The item goes back to Waiting with `Recovery.check` set, so it's held as `Hold::BrowserCheck { site, files }`, whose `until` is never (`i64::MAX`): it never starts by itself, Try Now refuses it, other downloads carry on, and Resume or Retry try afresh. `QueueRun` sets it aside (`has_ended`), so the run can end without it, and `RunEvent::NeedsCheck` gives a notification under `notify_failures`. The queue row's Open Check calls `open_check_window`, which asks `DownloadQueue::check_for` and shows the pages in the check window: one `WebviewWindow` (label `check`), titled "MediaFire Check" (", File 2 of 3"), with its own lasting profile in the data folder's `browser\` (`DataPaths::browser_folder`), no capability, remote pages only (Tauri keeps remote origins from the app's commands; `is_web_page` refuses local ones) and never leaving the site (`stays_on_site`, `CheckPage::on_site`), every permission refused but automatic downloads. When the page goes to its file's download address (`CheckPage::takes`: MediaFire's `download<n>.mediafire.com/<token>/<key>/…` with the page's key), `take` catches it in `on_navigation` and cancels the navigation, so the WebView never fetches the file; a download that starts anyway is stopped in `on_download` (returning false) and caught the same way. In testing, a real click on MediaFire's button reached `on_navigation` but never `on_download` (WebView2 started and stopped the download without Tauri passing it on), hence catching on navigation. A window the page opens (MediaFire's ad script opens `about:blank`, then sends the file there and the page to an advert) is a hidden `check-opened-<n>` window sharing the profile (`window_features`), which catches or refuses its first navigation and is destroyed. The window then shows the next page, or closes; what it caught goes to `DownloadQueue::passed_check`, which keeps the addresses in `QueueItem.caught_links` (in memory) and drops the pages they get past (`BrowserCheck::passed`). Closing the window early hands over what was caught. The next run applies them (`JobSpec.caught_links`, `Share::use_caught_links`), as `MediaFireFile.direct`. A pasted or copied `download<n>` link a waiting check takes is given to that download instead of being added (`insert_post` → `pass_check_with`), and the preview card and Pending don't call its video "in the queue" (`contains_video`). Tsundoku never presses anything in the window. Development builds: `TSUNDOKU_CHECK_LINK=<link>` opens the window on a link's files at startup and prints what it catches, `TSUNDOKU_CHECK_LINK=<queue ID>` opens it for that download once held, and `TSUNDOKU_CHECK_DEBUG_PORT` opens DevTools on its own port (`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` overrides it, so leave that unset).
- **Google Drive**: a file downloads from `https://drive.usercontent.google.com/download?id=ID&export=download&confirm=t` (plus `&resourcekey=KEY` when the link has one): `confirm=t` skips the virus scan warning on files over 100 MB, with no cookie or form. `hosts::probe` asks for `Range: bytes=0-0`, for the name (Content-Disposition, `filename*` first), size (Content-Range) and date (Last-Modified). An empty file has no first byte: Drive answers 416 without a size, so a 416 is asked again with HEAD, whose 200 attachment gives Content-Length 0 (a Google Doc answers 500 there). A folder is read from `https://drive.google.com/embeddedfolderview?id=ID`, plain HTML: its name is the page title, and each item is a `flip-entry` (`id="entry-ID"`) whose link is a subfolder (`/drive/folders/ID`), a file (`/file/d/ID/view`) or a Google Doc, Sheet or Slides on docs.google.com, which is left out. It has no sizes, so each file is probed, 8 at a time; unlike the `_DRIVE_ivd` data on the folder's own page, it isn't capped at 50 entries. A redirect to accounts.google.com means the item isn't public, and `uc-error-subcaption` "Too many users have viewed or downloaded this file recently" is LimitReached.
- **Dropbox**: a file downloads from its link with `dl=1`, which redirects to `*.dl.dropboxusercontent.com` (Range works), probed the same way. `/scl/` links need their `rlkey` (LinkIncomplete without it); old `/s/` and `/sh/` links don't, and an `/sh/` folder redirects to its `/scl/fo/` form. A folder is listed by the web page's own call, `POST https://www.dropbox.com/list_shared_link_folder_entries` with the form fields `is_xhr=true`, `t`, `link_key`, `secure_hash`, `link_type=c`, `sub_path` (no leading "/"), `rlkey`, and `voucher` (the last answer's `next_request_voucher`) while `has_more_entries`. `t` only has to match a `t` cookie, so any value works. Entries have `filename`, `is_dir`, `bytes` and `href`: a subfolder is listed with its own hash (the second segment of its `href`) and its path, and a file downloads from its `href` with `dl=1`. Errors are pages with status 200, told apart by their title ("Error", "Invalid Link", "No Access", "Log in to Dropbox").
- **OneDrive** (personal; `hosts/onedrive.rs`): read as OneDrive's own page reads a public link. `POST https://api-badgerp.svc.ms/v1.0/token` with `{"appId": "5cbed6ac-a083-4e14-b191-b4ba07653de2"}` gives an anonymous token (kept an hour, replaced when a request answers 401), sent as `Authorization: Badger <token>` with `Prefer: autoredeem` to `https://my.microsoftpersonalcontent.com/_api/v2.0/shares/u!<link in unpadded URL-safe base64>/driveitem`, then `…/driveitem/children` for a folder (paged by `@odata.nextLink`, followed only on that API and for the same share, `is_own_page`: a big folder's next page names the owner first, `/personal/<id>/_api/v2.0/shares('u!…')/…`). Every request names the shared link, so nothing outside it is reached. Tried live on 2026-11-11, OneDrive answers `itemNotFound` for `…/items/<id>` and `…/items/<id>/children` inside a shared folder, and 500 for `driveitem/children/<id>/children`: only the shared folder's own level can be read. So a subfolder with anything in it (`folder.childCount` above 0) makes the read `PreviewError::NestedFolders`, and a folder's file gets its download address from the folder's listing (`listed_file`, kept 10 minutes in `LISTING` so a folder's files don't each list it again); the web viewer's `/drives/<id>/items/<id>/children` doesn't name the share and wasn't tried. ### History

- `tsundoku.db` is SQLite (`rusqlite`, bundled), in WAL mode with foreign keys on, shared by the history and the queue through `database.rs`. Migrations are SQL strings there, applied in order and counted in `PRAGMA user_version`; never change a released one, add one. A database from a newer version is refused rather than read.
- `videos` holds one row per site and ID (with `post_images` and `post_videos` for a post); `downloads` one row per finished download, removed with its video (`ON DELETE CASCADE`); `download_files` every file of a download that made several (a post), with its number in the post (`post_number`, NULL for posts downloaded before it was kept), removed with its download. A video's download has no `download_files` rows: its `file_path` is the file. Times are seconds since 1970.
- `archive.txt` is rewritten whole (atomically) after every change and when the history opens, in the order videos were first downloaded.
- The UI names a download by its ID to open it or show it in its folder, never by a path, so it can only open files the history recorded.

### History View

- The history view is a list of cards, not a table: the window's minimum width (760 px) can't fit eight columns and a readable title. Sorting is a select with a direction button; it covers every column `HistorySort` has.
- **Thousands of rows**: it reads its results a page at a time (`History::page`, 100 videos from an offset, with the total for its count; `useHistory` is an infinite query that reads the next page 30 rows before the end), and draws only the rows on screen and 600 px around them (`useVirtualRows` in `virtualRows.ts`). The rows not drawn are two spacers, so the rows drawn stay in the normal flow: each is measured by a `ResizeObserver` (the 12 px between rows is its own padding, so it's measured too), and when a row above the screen changes height, Chromium's scroll anchoring keeps the screen still. Spacers rather than padding, which is a suppression trigger for scroll anchoring on an ancestor. Which rows are expanded is kept in the view, so a row scrolled away comes back as it was. The search waits 250 ms after typing (`useDebouncedValue`). TanStack Virtual was tried and dropped: `react-hooks/incompatible-library` warns on its `useVirtualizer`.
- Whether files are still there is checked for the page read only, once the database lock is released (`PastDownload::with_file_checked`), not for the whole history. With 5,000 videos (`history::tests::measure_at_scale`, ignored, run with `--ignored --nocapture`), a page takes about 15 ms against 400 ms for the whole list, and the view opens in about 20 ms against 1.5 s.
- Its results refetch when a download finishes (a queue item turns done) and after Forget. Every page shown is read again, from the first, so they stay in step.
- **Filters** run in the core with the paging (`filter_of`): Kind matches any download of the video (`downloads.kind`, migration 8, written by the queue from `RuleSubject::kind`; downloads from before are worked out from the video and the format, and from the preset's name when the format names no codecs), the date range the latest download's date (`downloaded_from` inclusive, `downloaded_until` exclusive; the UI works the bounds out when a range is picked, `historyDates.ts`, so the query doesn't move). The Files list (`HistoryQuery.files`, `FileState`) matches the File Missing pill, or its opposite: the latest download's file. Whether a file is there is only known from the disk, so the first page of a query with `files` set (`offset` 0) and `ids` check every video the other filters take (`note_missing`, 8 threads) and write the missing ones to `temp.missing_files`, a table that lives only while the app runs; later pages go by it, so they stay in step with the first.
- **Ticked rows**: Pending's pattern, a tick box per row and one for them all with the count. Ticking them all asks the core for every matching ID (`history_ids`), not only the rows read. What's ticked belongs to the query: a new search or filter starts with nothing ticked, so a ticked row the new results hide can't be forgotten unseen. Forget Selected asks once and calls `History::forget_all` (one transaction, `archive.txt` rewritten once); Show Selected in Folder counts the folders first (`history_folder_count`, ignoring letter case), says so when no file is left, asks when there are more than 5, then `show_videos_in_folders` passes every file to the opener's `reveal_items_in_dir`, which opens each folder once with its files selected.
- **Moving files** (`History::move_files`, the `move_history_files` command, `core::relocate`): every file of every download of the videos (`download_files`, else `downloads.file_path`) that's still there goes into the folder picked, relative to `relocate::common_folder` of its download's files, so subfolders come along. `relocate::move_file` makes the folder, takes a free name (`downloads::free_name`, " (2)"), and copies then deletes when `rename` fails (another drive), keeping only one copy if the delete fails. The rows' paths are updated in one transaction (`downloads.file_path` where it was the old path, so a post's first file follows too). `MovedFiles` counts moved and missing files and lists failures (`FailedMove`). Folders left empty stay.
- **Kept thumbnails** (`core::thumbnails`): a row shows the thumbnail kept in the data folder's `thumbnails\`, else the site's picture, else the empty tile (`Thumbnail`'s `fallbackUrl`), since sites' links expire (Instagram signs its image links) or go with a deleted post. Each is a 224×126 JPEG (twice the row's 112 px, cropped to 16:9 as the row shows it, about 6 KB) named `<site>-<16 hex of SHA-256 of site and ID>.jpg` (`file_name`), held in `videos.thumbnail_file` (migration 10: NULL until made, "" when none can be). The worker (`Thumbnails`, started in `open_data`) settles the folder with the history once at startup (a name whose file is missing, as after restoring a backup, is made again; a file no video names is deleted), then makes what's missing, newest first, every 15 seconds and a quarter of a second apart, so a new download gets its thumbnail within seconds and older rows follow. Sources, best first (`History::needing_thumbnails`): a post's first file, then its picture on the site; a video's or song's picture on the site, then a frame (or the cover art) of its own file; none for a file host's files. `FfmpegMaker` reads a site's picture with `hosts::client` (a 4xx means it's gone) and runs Tsundoku's ffmpeg: `thumbnail=30` picks a representative frame among the first 30, then it's scaled to cover 224×126 and cropped, written beside the target and renamed. A video none of whose sources can ever work gets ""; one that might later (offline, ffmpeg not set up) is tried again at the next start, not before. Forget deletes the file (`History::with_thumbnails_folder`). The window reads them through the `thumbnail` protocol (`history::serve_thumbnail`, `http://thumbnail.localhost/<name>` in WebView2, `keptThumbnailUrl` in `api.ts` through `convertFileSrc`), which serves only names `thumbnails::is_file_name` accepts, from that folder; the CSP's `img-src` allows it.
- Download Again in the history puts the video's link in the add bar and opens its preview (`AppActionsContext.showLink`), so the preset is picked and the duplicate warning shown as for any link.

### Presets and Downloads

- [Download Pipeline](./DOCUMENTATION/Docs/Download%20Pipeline.md) covers the queue's states, yt-dlp's arguments, the progress lines, temporary folders and logs.
- Presets live in `settings.json` (`presets.list`, `presets.defaultId`); the four built-ins have fixed IDs and can be reset, others are `custom-<n>` (`next_custom_id`). The default is always first: `PresetManager::overview` and `set_default` put it there (`default_first`), and `move_to` (the `move_preset` command) never places a preset above it. Any preset but the default can be deleted (`PresetError::IsDefault`), the built-ins included; `PresetsOverview.removed_built_ins` lists the deleted ones, which `reset` puts back at the end. `add` (`add_preset`) adds one set up as Best Video ships. `Preset::to_args` gives a preset's yt-dlp arguments, and both the editor and the queue use it.
- Extra arguments are split on spaces with double quotes grouping, backslashes left alone for Windows paths. Options that would break progress, paths, the history or the single-video rule are refused, abbreviations included, since yt-dlp accepts them (`--outp` for `--output`); `--progress` is allowed though it begins `--progress-template`.
- A queue item stores a copy of its preset and its resolved folder, so editing a preset or the download folder later doesn't change it.
- **A folder picked for one download** (migration 11): `pending_links.folder` (`PendingLink.folder`, `PendingLinks::set_folder`, the `set_pending_folder` command) goes with the link when it starts; `add_in`, `add_post_in` and `QueuePick.folder` take one for the queue, and `DownloadQueue::set_folder` (`set_queue_folder`) changes a waiting, stopped or failed item's, deleting its temporary folder when the folder changes, since it lives in the destination. Either wins over the rules (`chosen_folder`: a folder that isn't a full path is inside the download folder), and `QueueItem.folder_chosen` (`queue_items.folder_chosen`) remembers it. The UI shows it as `DestinationSource::Chosen` ("Picked for This One"); `DestinationLine`'s `onChoose` picks and drops it.
- **A rule picked for one link** (migration 14; Pending's Apply a Rule…): `pending_links.rule` (`PendingLink.rule_id`, `PendingLinks::set_rule`, the `set_pending_rule` command) goes with the link when it starts (`add_in` and `add_post_in` take a `rule_id`), and `queue_items.rule` (`QueueItem.rule_id`) keeps it, so `DownloadQueue::set_folder(None)` gives its folder back. `rules::picked_rule` finds it by ID: `destination`, `start_preset` and `file_name` take it (`picked`) and let it decide what it sets before any other rule, whatever its conditions and even while it's off; what it doesn't set goes to the rules as usual. Its `{1}` to `{9}` take nothing when its pattern doesn't match (`captured_when_picked`). A picked folder still wins over it. `download_destination` and `rule_preset` take a `ruleId`; in the UI, `DestinationRequest.ruleId`, `useRulePresets`'s `ruleIds`, and `DestinationLine`'s `chosenRuleId` and `onChooseRule` (a `Menu` of every rule, `Undo2` for Use the Matching Rules), which names the rule picked by comparing its number with the destination's source. The Queue's group by rule passes `QueueItem.rule_id`.
- **Where a download goes**: `rules::destination`, through `DownloadQueue::destination`, which both adding and the preview card (`download_destination`) use. The last rule that's on, picks a folder and whose conditions all match gives the folder (the bottom-most in the Rules view); else the preset's own folder (`Preset::own_folder`); else the download folder, `DownloadSettings::resolved_folder`: the chosen folder or `settings::default_download_folder` (`Downloads\Tsundoku`). `PresetsOverview.default_folder` carries the download folder to the preset editor, so Settings refetches the presets and destinations after changing it.
- **Folder rules** live in `settings.json` (`rules.list`), in order. Each condition joins the one before it with `RuleCondition.join` (`ConditionJoin::All` for AND, `Any` for OR, `#[serde(default)]` AND; the first's is ignored). OR binds first (`FolderRule::matches`): conditions joined by OR form groups, one of which must match, and every group joined by AND must, so "A OR B AND C" is (A or B) and C, which is how Fuzen reads it. 0.1.89 and 0.1.90 had one join for the whole rule (`FolderRule.join`, now read only: `#[serde(skip_serializing)]`, `#[ts(skip)]`), which `with_joins_on_conditions`, in `with_catch_all_first`, moves onto each condition. A rule without conditions matches every download. Conditions compare text ignoring case (unless `RuleCondition.case_sensitive`, `#[serde(default)]`, which `minds_case` ignores for the kind and the preset; a pattern then compiles without `case_insensitive`) and the spaces around the value, against every name the download's value goes by: a site matches its extractor key (`twitter`), its domain (`x.com`) and its `SIGN_IN_SITES` name (`X`); a preset its ID and its name. An uploader is its name (`uploader`) and its handle (`account`: yt-dlp's `uploader_id` through `metadata::handle`, which drops the "@" and leaves out numbers and YouTube channel IDs; gallery-dl's field for each site in `gallery::account`, the same ones as `post_names`). A missing uploader never equals, contains or matches anything. Matches and Doesn't Match (`RuleCondition::is_pattern`) compile the value with the `regex` crate, ignoring case (`RegexBuilder::case_insensitive`), and look for it anywhere; `validate` refuses a pattern that doesn't compile as `RuleError::InvalidPattern`, with the crate's one-line reason (`pattern_problem`), and one that slipped in anyway matches nothing. `rules::placeholder_value` fills a folder's placeholders in any case: `{site}` (`rules::site_name`: the sign-in name, else the file host's name, else the extractor key), `{uploader}`, `{account}` (else the uploader), `{playlist}` (`VideoInfo.playlist`, else No Playlist), `{title}`, `{id}`, `{kind}` (`DownloadKind::folder_name`), `{preset}` (the kind's name without one), `{year}`, `{month}` and `{date}` from `upload_date`, `{added}` (the local date, `local_date`; tests pass one to `destination_on`), and `{1}` to `{9}` from the rule's first Matches pattern with groups (`FolderRule::captured`), each made safe as one folder's name and cut to 80 characters (`folder_part`), with Unknown (Untitled, or the kind) for a missing value; other braces, and `{1}` in a rule without such a pattern, stay. **Missing values** (0.1.102, Fuzen's ask: `{site}\{account}` saved a MediaFire file in `MediaFire\Unknown`): `FolderRule.missing_values` (`MissingValues`, `#[serde(default)]` `StandIn`, so rules saved before keep Unknown) set to `LeaveOut` makes `placeholder_value` answer `NamePart::Value(None)` for a missing value instead of the stand-in. `fill_placeholders` fills the folder one name at a time between separators (`fill_folder_name`): a name whose placeholders all have no value goes with its separator (`{site}\{account}` is `MediaFire`, `D:\{account}` is `D:\`), one with some keeps them, each missing one going with the text before it, or after it when it's the first (`name_parts::join_leaving_out`, the rule posts' names already had for an unknown date), and an empty result is the download folder (`inside_download_folder`). In `StandIn` the output is what it was. A watched source's Save In (`filled_folder`) always uses `StandIn`. A folder that isn't absolute is joined to the download folder. The catch-all (`catch-all`, no conditions, `{site}` to start with) is always first, so every other rule overrides it, and comes after a preset's own folder: `rules::destination` takes the last matching rule other than it, then `Preset::own_folder`, then the catch-all when it's on, then the download folder. **Order**: since 0.1.86 the last matching rule decides (Fuzen's choice, so a rule added at the bottom overrides those above it); before, the first one did, with the catch-all last. `RulesSettings.last_wins` (`lastWins`, missing in a file from before) tells them apart: `Settings::from_json` reverses a list without it, so each rule keeps deciding what it did, and sets it. An older version reads a list saved since as first-wins, so its rules then decide in reverse. `rules::with_catch_all_first`, applied when settings are read and in `RuleManager::save`, moves it to the top, drops any conditions, turns the posts rule of 0.1.11 to 0.1.29 (`posts`, "kind is post → {site}") into it, keeping its folder and whether it's on, and puts it back turned off if it's missing, so it can't be deleted; the Rules view adds new rules at the bottom, doesn't offer to move, duplicate or delete it, and its editor has no conditions. `Settings::from_json` turns a saved `downloads.postsFolder` (0.1.8 to 0.1.10) into a "kind is post" rule (`rules::posts_folder_rule`) below the catch-all when the file has no `rules` yet. `RuleManager::save` replaces the whole list, trimmed and checked, and gives new rules (an empty ID) `rule-<n>`.
- **Names**: `FolderRule.name` (`#[serde(default)]`, trimmed when saved, empty for none). The core still answers rules by number (`DestinationSource::Rule`, `RulePreset.rule`, `RightAwayRule.rule`), and the UI names them with `ruleLabel` (`views/rules/ruleLabels.ts`; `useRuleLabel` in `queries.ts`), the rule's name else "Rule N": `DestinationLine`, `PresetRuleLink`, Test a Link, the delete question and `ruleGroup`. Save errors (`RuleError`) still say "Rule N", since they show in the rule's own editor.
- **File names** (0.1.96; as posts' names since 0.1.97; captures and shared files since 0.1.99): `FolderRule.file_name` (`#[serde(default)]`, trimmed) is written as Settings → Posts of Images' name plus `{1}` to `{9}`, and refused by `post_names::check_text` (forbidden characters and unknown placeholders; `{post}` and `{number}` aren't required) as `RuleError::FileName`. `rules::file_name` takes the last rule that's on, names files and matches (never the catch-all), fills `{1}` to `{9}` from its pattern and takes out an unknown `{date}` and, with `MissingValues::LeaveOut`, an `{account}` the download has none of (`post_names::fill_rule_name`; `post_names::parse` reads `{1}` to `{9}` as `Part::Group`, which stay text in Settings' name), each with its separator, so a group that took no part leaves no separator behind either, and answers for a post (with ` {post}` and ` {number}` added when it lacks them, `{numberIfMany}` counting as a number) or a file host's link of one file (filled by `post_names::shared_file_name`, without the extension); `None` for a video and a shared folder. `DownloadQueue::insert_post` keeps it in `QueueItem.file_name` (`queue_items.file_name`, migration 13; `#[serde(skip)]`); `job_for` passes a post's to `post_names::gallery_format` in place of Settings' name and a shared file's as `JobSpec.shared_file_name`, which `file_runner` uses (`destination_of`, keeping the file's extension) when the share still has one file. The UI's field is `components/PostNameInput.tsx`, shared with Settings. `PostNamePlaceholder::NumberIfMany` (`{numberIfMany}`) is the number only when the post's picked files are several (`post_file_count`), left out with its separator otherwise, and counts as `{number}` for `check`.
- **What else a rule does**: a `FolderRule` also has `preset_id` and `download_right_away`, `None` when unset (`#[serde(default)]`, so rules saved before read as they were), and its `folder` may be empty when it only does those (empty rather than missing, so an older version still reads the rule). Each of the three is decided on its own: the last rule that's on, sets it and matches. `rules::start_preset` (`RuleManager::start_preset`, the `rule_preset` command, `useRulePreset` and `useRulePresets` in the UI) picks the preset for a video, matching it with no preset, so a rule that checks the kind or the preset can't pick one (`can_pick_preset`; `RuleManager::save` refuses it as `CircularPreset`), and passes over a preset that no longer exists. A video starts with the card's or the pending link's own pick, else the rule's, else Videos Start As or the default (`PendingLinks::start_preset`); a link started before it was read takes the rule's over the Videos Start As preset kept when it was started. `rules::right_away_rule` (the `rule_download_right_away` command, `useRuleRightAway`) gives the same with the deciding rule's number, for Rules' Test a Link (`views/rules/RuleTester.tsx`), which reads the link with `fetchPreview` and asks `useRulePreset`, `useDownloadDestination` and it. `rules::download_right_away` overrides `AddingSettings.download_right_away` for copied links and sent ones: a sent link is `StartWhenRead::IfRightAway` (2 in `pending_links.start_when_read`, no migration; an older version reads it as started) and is decided once read, like a caught one. A rule must do something (`NoAction`), and the catch-all only picks a folder (`with_catch_all_first` clears the rest).
- **Grouping and sorting** the Pending and Queue views (`settings.lists`, `ListArrangements`: `list_arrangements` and `save_list_arrangements`): each view keeps a `ListArrangement` (`byStatus`; `group`: none, destination, site or rule; `sort`: added, title, uploader or site; `descending`). Before 0.1.69 status was one of the groups: `StoredListArrangement` reads `"group": "status"` as `byStatus` with no group (`ListArrangement`'s own `Deserialize`, since ts-rs can't read `#[serde(from)]`). The UI does the work: `arrange.ts` sorts (missing values last, ties by ID) and groups (`GroupPlace`: rank, then label; `arrangeNested` groups by status, then by the other grouping within each as `subgroups`, `NO_GROUP` for an item without one), `ruleGroup` (through `useRuleGroupOf`) names a rule's group by its number and `fixedFolder`, the rule's folder up to its first placeholder, `components/ArrangedList.tsx` has the toolbar's controls and the grouped list, and `useListArrangement` applies a change at once and saves it, undoing it if saving fails. Pending groups by folder and by rule through `useDownloadDestinations`, which shares its answers with the rows' destination lines; the Queue asks it only to group by rule, since its items keep their folder but not what picked it (so a rule changed since shows as it is now). Folded groups live in `GroupedList`'s state, kept per view in a module-level set while the app runs (`collapsedByView`), not in the settings; Pending passes `selection`, which puts a box on each heading that ticks its group, and its rows drop the destination's folder when grouped by it (`DestinationLine`'s `folderShown`). `Settings.lists` is read with `default_if_unreadable`, so a choice from a newer version only resets the arrangements instead of setting `settings.json` aside.
- **Pending links** (`core::pending`, the Pending view): text pasted or dropped with several links in it (`pending::links_in`, through `links_in_text`) goes to `PendingLinks` instead of the preview card. They live in `tsundoku.db` (`pending_links`, migration 5), the video as JSON once read. One thread reads them one at a time through `LinkReader` (`preview::ToolReader`, the preview card's own reading without its one-at-a-time cancelling; tests use a fake), oldest first, skipping links on a paced site while the pause after its last one runs (`paced_until`, one per `sites::PacedSite`, from `DownloadSettings::pause_for`). The duplicate warning and "in the queue" are worked out each time the list is read, so they follow the history; the UI refetches the list on `queue-changed` too. `start` queues a read link with its own preset or the one given (falling back to the default if it was deleted), or marks a link not read yet `start_when_read`, which queues it once read unless the history has it. A second link to a video already here is dropped once read. `pending-changed` carries every link.
- **Files of links** (`pending::files`, dropped anywhere on the window): `useLinkDrop` takes a drop's text and its `File`s (WebView2 hands the page both while `dragDropEnabled` is false; Tauri's own drop handling, the only way to get the files' paths, would replace WebView2's drop target and lose dropped links). A drop's files win over its text when one of them is a kind Tsundoku reads, else the text goes in as before, so a linked image dragged from a browser still gives its link. `readLinkFiles` asks the core first (`check_link_file`: the extension, `.txt`, `.html`/`.htm` or `.url`, and at most `MAX_FILE_BYTES`, 10 MB), then sends the bytes as a raw request (`links_in_link_file`, the name as ASCII JSON in the `tsundoku-file-name` header). `files::links_in_file` decodes them (UTF-16 by its byte order mark, else UTF-8 with replacement characters) and keeps http and https links only: a text file's words written with their scheme (`links_in`), a bookmarks export's `<a href>`s with their entities decoded (so `place:`, `javascript:` and `data:` drop out), an Internet shortcut's `URL=` under `[InternetShortcut]`. Over `ASK_BEFORE_ADDING_OVER` (300) links, the UI asks first with `checkingTime` (2.5 s a link). They're added with `add_from_files`, as `LinkOrigin::File` (`pending_links.caught` = 2; 0 is added by hand, 1 copied, so an older version reads them as copied). `PendingLinks::leaves_once_read` is the one rule for which links stay: a link from a file is read with yt-dlp's generic extractor off and leaves when there's nothing to download, as a copied one does, but stays when the history or the queue has its video, as one added by hand does; it's never announced and never downloaded right away. The UI hides it until read (`fromFile`) and counts it apart ("Checking 1,234 links from files…").
- **Thousands of pending links**: `insert` saves new links in one transaction (`PendingStore::insert_all`) and looks the links already here up in a set. `notify` sends `pending-changed` at once when the last went out more than `change_gap` ago (250 ms, 1 s over 500 links), else leaves it to `send_due_notices`, which sends one with the list as it is then once the gap is up. The Pending view shows `PENDING_PAGE` (200) rows, and Show More adds as many (`firstItems` in `arrange.ts`).
- **Ways to add links** (`components/WaysToAdd.tsx`, on the empty Queue and Pending): each row works through `AppActions`: Paste reads the clipboard (`clipboard_text`, the clipboard shortcut's `clipboard::copied_text`) and calls `addText`, the add bar's own; Choose File… asks for files with the dialog plugin (`pickLinkFiles`) and the core reads them by path (`links_in_file_at`, `files::links_in_path`, off the main thread), then `addFileLinks` takes them as a drop's (asking over 300, `fileProblems`); Turn On saves `watchClipboard`; Set Up and Change call `navigate("settings", place)` with a `SETTINGS_PLACES` ID, and `SettingsView` scrolls to that element and focuses its control (a new `SettingsTarget` object each time, so asking again scrolls again).
- **Clipboard watcher** (`pending::watcher`, Settings → Adding Links: `settings.adding`, `adding_options` and `save_adding_options`): a thread looks at the clipboard's change count every 500 ms (`Clipboard`, on Windows `clipboard::SystemClipboard`: `GetClipboardSequenceNumber`), and reads the text only when it changed while the watcher is on, so what was copied before turning it on is skipped. `SystemClipboard::text` refuses copies owned by Tsundoku's process or its children (WebView2 copies from its own process, found through ToolHelp) and copies carrying `ExcludeClipboardContentFromMonitorProcessing` or `Clipboard Viewer Ignore` (password managers). `watcher::copied_links` takes a copy only when every word is an http(s) link, minus direct file links (`FILE_ENDINGS`, never a file host's). `PendingLinks::catch` adds them with `caught` set (migration 6), skipping links the queue or the history has by the exact address (`has_link`). A caught link is read with yt-dlp's generic extractor off (`LinkReader::read`'s `any_page`, `--ies default,-generic`, which turns down unknown sites offline as "No suitable extractor"). Once read it leaves quietly when there's nothing to download (`nothing_to_download`: unsupported, no video, a playlist, an invalid link, or images without gallery-dl on a site not about images; a file host's link its `parse_link` doesn't take is `LinkNotRecognized`, from `Host::link_not_recognized`, not `UnsupportedSite`, so it stays to say so) or the queue or history has its video; with `download_right_away` the rest go through `start_once_read`. The UI hides caught links until read (`shownPendingLinks`) and counts them as being checked.
- **Undo after removing**: `PendingLinks::remove` and `DownloadQueue::clear_finished` remove for real at once (the tray, the clipboard watcher's duplicate check and a restart all see it), answer how many went, and keep what they took in memory until the next removal (`Contents.removed`, `QueueContents.cleared`). A finished queue item also leaves on its own (`remove_finished`, the `remove_finished_download` command), through the same `clear_done` as Clear Finished, so Undo is `restore_cleared` too. `restore_removed` and `restore_cleared` (the `restore_removed_pending_links` and `restore_cleared_downloads` commands) save them again with their own IDs, so they take their places again (pending links are in the order of IDs; a queue item goes back to its index and to the `position` that `QueueStore::take` returned), keep their logs, and come back ticked in Pending, whose selection keeps removed IDs. One whose address, or video once read, is back by then stays out. The UI offers Undo through `useOfferUndo` (`undo.ts`), which `components/UndoToast.tsx` shows.
- `DownloadQueue` owns its items and runs each download on a thread of its own; `QueueListener` passes changes and progress to the app crate, which sends them as events. The runner is a trait (`JobRunner`), so tests swap yt-dlp for `FakeRunner`.
- **The whole queue**: `stop_all` (Pause All), `resume_all` and `retry_failed` do `stop`, `resume` and `retry` for every item in the state each acts on (`requeue_all` and `put_back_in_line` are shared with the single-item ones). `download_next` moves a waiting item to the front of `items` and saves it in `queue_items.position` (migration 7: 0 when added, one less than the lowest when moved), which `QueueStore::load` orders by, then ID. The tray's Pause All Downloads follows `WholeQueueAction::for_items`: pause while anything runs or waits, else resume while anything is stopped.
- **The queue's run** (`downloads::run`, [Download Pipeline](./DOCUMENTATION/Docs/Download%20Pipeline.md#the-run)): `QueueRun` follows the queue's items and progress from the downloads started since the queue was last idle until each has ended, and `RunSummary` gives the taskbar's state (`TaskbarProgress`) and the tray's tooltip text, which lives there rather than in `background.rs` so it's tested. `src-tauri/src/queue_status.rs` (`QueueStatus`, fed by `downloads::EventListener`) works out what should show and has the main thread show it (`set_progress_bar`, `background::set_tray_tooltip`), never under its lock, since the tray's setters wait for the main thread; progress alone at most every 250 ms.
- **Too many requests** (`site_limits`, `downloads/holds.rs`): yt-dlp's and gallery-dl's errors saying a site answered HTTP 429 (`TOO_MANY_REQUESTS_PHRASES`: "HTTP Error 429", "'429 Too Many Requests'", "rate-limited", Instagram's "Please wait a few minutes") are `PreviewError::TooManyRequests`, checked after the sign-in phrases, since yt-dlp's "rate-limit reached or login required" may mean a sign-in. That one (`PreviewError::may_be_slow_down`) becomes `TooManyRequests` on Instagram when a browser profile of the cookies choice is signed in to it (`browsers::slow_down_if_signed_in`, Fuzen's answer): previews and Pending's reads in `preview::with_sign_in_state`, downloads in the run's thread before `finish`, outside the queue's lock. Neither tool passes on Retry-After, so the wait is Tsundoku's own: `SiteLimits` keeps one per site (`sites::site_of`: a sign-in site or file host by its name, any other by its domain's last two labels), 5 minutes doubled for each 429 since the site last worked, up to an hour, and forgotten an hour after it ended; a 429 during a wait doesn't lengthen it. The queue owns it: a run that ends that way goes back to Waiting instead of Failed (`finish`, `asked_to_slow_down`), `schedule` first gives every waiting item its `Hold` (`settle_holds`: the site's wait, then the hourly limit) and starts only those without one, and `watch_holds` schedules again within a second of one ending. The pending links' reader skips a waiting site's links (`readable`) and puts one that got a 429 back to Waiting, and the preview card doesn't read while the site waits (`site_wait`), filling in the site and time. A download from the site finishing, or a link on it read, resets its count (`site_worked`). Waits and holds live in memory: after a restart, a waiting download tries once, and waits again if the site still refuses. Pause All, Resume All and Retry Failed need nothing of their own, since holds are only worked out for waiting items.
- **Hourly limit** (`downloads.hourlyFileLimit`, Settings → Pacing): on Instagram, `hold_for` asks the history for the site's downloads in the past hour (`History::recent_downloads`: the files of each from `download_files`, one for a video) and `site_limits::hourly_limit_end` gives when enough of them are an hour old to leave room for this one's files (a post's images and videos, one for a video). One bigger than the limit waits for an empty hour. `None`, the default, or 0 is no limit.
- **Room on the drive** (`room`, `downloads/room_check.rs`): `schedule` checks each waiting item as it's about to start, after its other holds: `room::expected_bytes` (a file host's `files.bytes`; for a video, `FormatSizes::estimate` of the formats its preset's `-f` picks, the tallest up to its height limit plus the best audio, or the best audio, from `filesize` else `filesize_approx`; `None` for a post or without sizes) against `DiskSpace::free` (`SystemDisks`: `GetDiskFreeSpaceExW` on the folder's nearest existing ancestor, for this user, quotas included) less `Reserved` (what the downloads running on the same drive, by `room::drive_name`, still need: expected less `downloaded_bytes`, and each one started in the same pass), with a margin of 100 MB and 5% (`room::shortfall`). One that won't fit gets `Hold::NotEnoughRoom` (the drive, its free bytes, what it needs with the margin, the running downloads' share) with `until` 30 s on, so `watch_holds` schedules again; `settle_holds` clears it each time and the loop tries the next item. `cancel` schedules too, since a removed item's partial files are gone. A video's format sizes are kept in memory by `parse_info` (`room::remember_sizes`, by site and ID, up to 5,000 videos), since `VideoInfo` doesn't carry them: a video added before a restart isn't checked. Tests swap the disk for a fake (`use_disk_space`), and `check_room_again` schedules at once. The UI's `holdEnd` shows no countdown for it.
- **Automatic retries** (`downloads/holds.rs`): a run that fails with `PreviewError::Network` or `LimitReached` goes back to Waiting with its own wait instead of Failed (`finish`, `Recovery::after_failure`): a lost connection after `CONNECTION_RETRY_WAITS` (30 s, 2 min, 8 min), then it fails; a used-up download limit after `limit_wait` (30 min doubled up to 4 h, `LONGEST_LIMIT_WAIT`), never failing. `QueueItem.recovery` (`#[serde(skip)]`, `#[ts(skip)]`) counts both and holds the wait, which `hold_for` gives as `Hold::Retry` or `Hold::LimitReached` before the site's wait and the hourly limit. It's reset by a finished run and by `put_back_in_line` (Resume, Retry, Resume All, Retry Failed), so the user's own start begins the retries over; a run the user stopped never retries. Per item, not per site: a MEGA limit is per connection, but each of its downloads finds out in one request. `try_now` (the `try_download_now` command) drops an item's own wait, or ends its site's "too many requests" wait (`SiteLimits::end`, keeping the count), and refuses the hourly limit, which is the user's own. In memory only, like the site waits.

- **Running in the background** (`src-tauri/src/background.rs`, Settings → Running in the Background: `settings.background`, `background_options` and `save_background_options`): the tray icon (Tauri's `tray-icon` feature) exists while `keep_in_tray` is on; its menu's changing items (`TrayMenu`) follow `PendingListener::changed` (Start All Pending's count, `pending::starts_with_all`) and `options_changed` (Watch Clipboard's tick, also sent to the UI as `adding-options-changed`), and the queue's `changed` (Pause All Downloads, `background::queue_changed`). Quit asks through the dialog plugin while downloads run. Start with Windows is `tauri-plugin-autostart`, applied when the setting is saved; Windows starts the app with `--in-tray`, and with the tray on the window then stays hidden (`AppInfo.started_in_tray`, which both the UI and the fallback in `lib.rs` check). Development builds register as "Tsundoku (Development)", apart from the installed app. The clipboard shortcut (`AddingSettings.clipboard_shortcut`, `tauri-plugin-global-shortcut`) is registered at startup and swapped in `save_adding_options` before saving, which fails with `DownloadError::ShortcutTaken` when Windows won't give the keys; pressing it reads the clipboard off the main thread (`clipboard::copied_text`, any owner) and adds its links with `PendingLinks::add_sent`, as if pasted but started once read with Download Right Away. Pages sent from a browser are `tsundoku://add?url=…` links (`pending::SEND_SCHEME`, `pending::links_in_sent_link`), which the Settings bookmark (`SEND_PAGE_BOOKMARK` in `sendPage.ts`, a `javascript:` bookmark copied with `copyText`) opens: `tauri-plugin-deep-link` (scheme in `tauri.conf.json`, so the installer registers it; `register_all` at each start too, pointing it at the build that ran last) reads it from a launch's only argument, and the single-instance plugin's `deep-link` feature hands a second launch's link to the running app, whose callback then leaves the window where it is (`background::is_sent_link`). They go through `add_sent` with a notification too; a launch for a sent page with the tray on starts hidden. Notifications (`tauri-plugin-notification`, from Rust only) go out when `AddingSettings.notify` is on and the window isn't visible, focused and unminimized: `PendingListener::copied_link_read` for each caught link that stays, the shortcut, sent pages, and the tray's Start All Pending. The queue's run events (`RunEvent`: a download failed, the run ended) come from `QueueStatus` to `background::queue_events`, which gathers them for 1.5 s (`GatheredEvents`) so failures that come together are one notification, words them with `downloads::notices` and tells them while the window isn't in front, each kind behind its own switch (`AddingSettings.notify_failures`, `notify_finished`) rather than `notify`. Clicking one focuses the window (`on_action`). The tray's and notifications' texts are in `background.rs`'s `text` module, since they show outside the UI.
