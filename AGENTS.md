## Introduction

- Tsundoku is a Windows desktop app (Tauri 2: a React + TypeScript UI over a Rust core) that downloads videos with yt-dlp and keeps a history of everything it has downloaded, so it can warn before a duplicate.
- [PROJECT.md](./PROJECT.md) holds the original spec and its decisions, [TODO.md](./TODO.md) the features planned after v1.

## Rules

- All UI text lives in `tsundoku/src/strings.ts`, in English. Never write UI text in a component.
- UI labels use Title Case: buttons, toggles, navigation, headings, dialog titles and buttons, placeholders, column headers and short names. Minor words (a, an, the, and, or, of, to, in, on, for, with, as, at, by, from) stay lowercase unless first or last, and hyphenated words take both capitals. Sentences (descriptions, messages, empty-state explanations, status texts) stay in sentence case. See [DESIGN](./DESIGN.md).
- `tsundoku-core` (`tsundoku/core`) has no Tauri dependency. Downloads, the history, the tools, presets and settings go there, with unit tests; the app crate (`tsundoku/src-tauri`) only exposes them as commands and events, and the UI only presents.
- Types the UI reads are Rust types in the core deriving `ts_rs::TS` with `#[ts(export)]`; `cargo test` writes them to `tsundoku/src/bindings`. Never hand-write a TypeScript type that mirrors a Rust one, and commit the regenerated files with the change.
- `tsundoku/src/api.ts` is the only place that calls `invoke` or another Tauri API.
- Before a visual change, read [DESIGN](./DESIGN.md). If something differs notably from it, tell the user.
- Never suppress, ignore or work around an ESLint, Clippy or TypeScript error or warning; fix the cause.
- Meta files (docs, scripts) go at the project root; `tsundoku/` holds code only.
- After implementing a feature, update [FEATURES](./FEATURES.md) and remove the item from [TODO](./TODO.md) if it is listed.
- Every change bumps the patch version and gets an entry in [CHANGELOG](./CHANGELOG.md); a commit that bumps the version is tagged `vX.Y.Z`. A release bumps the minor or major version and folds in the patch entries since the previous release.

## Technical Notes

- The main window starts hidden and transparent (`tauri.conf.json`). `src-tauri/src/lib.rs` applies Mica, which needs Windows 11, and records whether it worked. `main.tsx` reads that through the `app_info` command before the first render and sets `data-backdrop` on `<html>`: `mica` makes the page transparent, `solid` paints `--color-bg`. `App` shows the window after its first frame, and Rust shows it anyway after 3 seconds if the UI never does.
- **Theme** (Settings → Appearance: `settings.appearance`, `appearance_options` and `save_appearance_options` in `src-tauri/src/appearance.rs`): `Theme::Auto`, `Light` or `Dark`. `appearance::apply_theme` calls the window's `set_theme` (`None` for Auto) in `setup`, while the window is still hidden, and again when the choice is saved. On Windows that sets the title bar's dark mode, which Mica's tint follows, and tao's `ThemeChanged` then makes tauri-runtime-wry set WebView2's preferred color scheme. The UI doesn't rely on that: `main.tsx` reads the options (`appearance_options`) with `app_info` before the first render and `theme.ts` sets `data-theme` on `<html>`, from which `index.css` sets `color-scheme` (`light`, `dark`, or `light dark` for Auto), so every `light-dark()` token follows. Choosing a theme sets `data-theme` at once, and back if saving fails.
- `single-instance` is the first plugin registered, as it requires: a second launch focuses the running window. `window-state` restores size, position and maximized state, never visibility.
- Every Tauri permission the UI uses is listed in `src-tauri/capabilities/default.json`; `core:window:allow-show` is there for the hidden start.
- The CSP in `tauri.conf.json` allows `https:` images, for video thumbnails. Network requests (GitHub) come from Rust, never from the UI.

### Releases

- A release is a version tag pushed to GitHub: `.github/workflows/release.yml` checks that the tag matches `package.json` and `Cargo.toml`, runs `Scripts\Check.cmd`, checks the committed bindings are current, then `tauri-action` builds the installer, signs it and publishes a release with `latest.json` for the updater, and a last step sets `.github/release-notes.md` as the release's text (`tauri-action` only takes it as a string). Running the workflow by hand builds without publishing or signing, and keeps the installer with the run: a way to test a build before tagging.
- Push the tag on its own, after the commit (`git push origin main`, then `git push origin vX.Y.Z`). The v0.1.0 tag, pushed in one go with the commit that first added the workflow, started no run.
- A run takes about 20 minutes without a cache and 10 with one.
- Releases aren't marked pre-release, even for 0.x: the updater reads `releases/latest/download/latest.json`, and GitHub's "latest" skips pre-releases.
- Signing: the private key and its password are the repository's `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` secrets; the user keeps the key file outside the repository. Only the public key is in `tauri.conf.json` (`plugins.updater.pubkey`). Losing the private key means installed copies can't update anymore: a new key needs a new install.
- `src-tauri/tauri.release.conf.json` turns on the updater's files (`createUpdaterArtifacts`) for the release build only, since making them needs the private key. `Scripts\Build.cmd` builds the installer without them.
- `requireSignedVersion` is on: the updater refuses a release whose signature names another version, so an older signed release can't be served as a newer one.
- The installer is NSIS, per-user (`installMode: currentUser`), into `%LocalAppData%\Tsundoku`. Updates install in passive mode: a progress bar, no questions.
- While the repository is private, the update check fails (GitHub won't serve its release files without signing in) and the app shows nothing; Settings → About shows the error.

### Portable Copies

- A release build whose exe has `.portable.txt` beside it (`data_folder::PORTABLE_MARKER`) is portable. `make_portable_if_marked` in `src-tauri/src/lib.rs` checks before Tauri starts and sets `app.appDirectoriesOverride` (Tauri 2.12) on the context's config to the `data` folder beside the exe, so every app folder follows: `app_local_data_dir` (the data folder, which `data_folder::resolve` takes for a release build), `app_config_dir` (window-state's file) and the WebView's `EBWebView`. Development builds ignore the marker.
- `data_folder::set_portable_folder` records the copy's folder for the core (`data_folder::portable_folder`): a download folder that isn't a full path is inside it (`settings::BESIDE_APP_DOWNLOADS`, "Downloads", chosen at setup), so it follows the copy to another drive. `AppInfo.portable` tells the UI.
- A portable copy doesn't check for updates (`useAppUpdate` is off): Tauri's updater only runs the NSIS installer, which would install Tsundoku instead of replacing the copy. Replacing the exe in place (a `windows-x86_64-portable` entry in `latest.json`, signed with `version:` in its trusted comment since `requireSignedVersion` is on) and a zip in the release run are for a public portable release, with registering the notification ID (`HKCU\Software\Classes\AppUserModelId\<identifier>`, which the installer's shortcut does otherwise) and re-pointing Start with Windows when the folder moves (`enable()` also re-approves the entry in Task Manager, so only when the path changed).
- `background::startup_name` makes Start with Windows "Tsundoku (Portable)", apart from an installed copy's "Tsundoku". Both copies share the single-instance lock (the identifier), so only one runs at a time, and the browser bookmark's `tsundoku://` follows whichever started last.

### First-Run Choices

- `first_run::options` and `save` (the `first_run_options` and `save_first_run_choices` commands): where the tools go (`ToolsSettings.folder`, `None` for the data folder's `tools\`), their caches (`ToolsSettings.caches`) and the download folder. They're `needed` while `tools.caches` is `None` and yt-dlp or ffmpeg isn't set up, so an install from before 0.1.20 is never asked. The UI's `SetupView` shows `ChoicesScreen` first, then `ToolsScreen`; saving sets `needed` to false in the query, and Back sets it to true.
- `ToolManager::tools_folder` is the chosen folder or the data folder's `tools\`, for installs, updates, finding Tsundoku's copies and running them.
- A portable copy is also offered an installed copy's `tools\` in AppData (`FirstRunOptions.installed_tools_folder`: Tauri's `local_data_dir`, which the override leaves alone, joined to the identifier), picked when `tools::has_own_copies` finds Tsundoku's copies there. The tools screen's detection then finds them as Tsundoku's own (`locate::candidates` looks in the tools folder first), and Use This Copy sets them up as managed with no stored checksum.
- `ToolCaches::DataFolder` gives runs a `ToolCacheFolder` (`ToolManager::cache_folder`) for the data folder's `cache\`: yt-dlp gets `--cache-dir cache\yt-dlp` and its Deno `DENO_DIR=cache\deno` (`ProgramCommand::variable`, inherited by the Deno yt-dlp starts), gallery-dl `-o cache.file=cache\gallery-dl\cache.sqlite3`, whose folder Tsundoku makes since gallery-dl silently keeps its cache in memory otherwise. `UsualFolders` or `None` passes nothing. Previews (`FetchTools`, `GalleryTools`) and downloads (`JobSpec`) both get it.

### Backups

- Settings → About's Back Up and Restore (`views/settings/BackupRow.tsx`) call `save_backup` and `restore_backup` (`src-tauri/src/backup.rs`), which run `core::backup::create` and `restore`. A backup is a zip: `manifest.json` (`format`, `appVersion`, `schemaVersion`, `createdAt`), `settings.json` without `tools`, `tsundoku.db` and `archive.txt`.
- The database is copied with `VACUUM INTO` on the open connection, so the copy is consistent while downloads run; the copy then loses `queue_items` and `pending_links` and is switched to `journal_mode=DELETE`, so it's one file. The app crate manages the `Arc<Database>` for this.
- A restore reads and checks everything before changing anything, in a working folder under the data folder's `backups\`: a `format` or `appVersion` newer than this one, or a database `Database::open` refuses, is `NewerVersion`; opening the database also migrates an older one. It then saves the current data there as "Tsundoku Backup <local date and time> (Before Restore).zip", replaces the settings (keeping this PC's `tools` and `background.startWithWindows`, whose Windows entry is only changed when saved, and dropping a download folder that isn't a full path unless the copy is portable), then the history's rows in one transaction through `ATTACH` (`SELECT *` works because both databases went through the same migrations), putting the settings back if that fails. Finished queue items are deleted, since their `result.downloadId` names a download in the replaced history. The UI restarts the app (`relaunch`) afterwards, so the shortcut, the tray, the theme and every query read what was restored.

### Running Programs

- `core::process` is the only place that starts yt-dlp, ffmpeg or Deno. Each starts without a console window (`CREATE_NO_WINDOW`), suspended, is put in a new job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, then resumed, so it can't start anything outside the job. Ending the job ends yt-dlp and the ffmpeg it started; closing the job's handle (when the app exits or crashes) does the same.
- process-wrap was tried and dropped: its job object for `std` never sets kill-on-close, so the tools would outlive a crash.
- Output is read line by line on two threads into a channel; a carriage return also ends a line. `run` polls every 100 ms for cancellation and its time limit.
- Tauri commands that run programs or download are `async` and do the work through `spawn_blocking`, since a sync command runs on the main thread and would freeze the window.

### Tools

- `core::tools::catalog` names each tool's release host, repository, release file and checksum file. gallery-dl (`mikf/gallery-dl`, the standalone `gallery-dl.exe`) comes from **Codeberg**, where its development moved in 2026: its GitHub releases since 1.32 have no files. Codeberg runs Forgejo, whose `/api/v1/repos/<repo>/releases/latest` answers in the same shape as GitHub's (`tag_name`, `published_at`, `assets` with `name`, `size` and `browser_download_url`), so `github.rs` reads both; its `SHA256SUMS` uses the `<hash>  <name>` form. Since 0.1.25 the first-run setup sets it up with the others (`ToolId::SETUP` is every tool, `setupToolOrder` in the UI), but like Deno it's optional: the setup can be left when only optional tools failed (`optionalTools`), and `needs_setup` asks only for yt-dlp and ffmpeg, so an install from before isn't sent back to it. It's run with `--config-ignore`, gallery-dl's spelling of yt-dlp's `--ignore-config`. ffmpeg comes from yt-dlp/FFmpeg-Builds' **shared** build (91 MB, 193 MB installed), not the static one (202 MB, 340 MB installed): ffmpeg and ffprobe share their DLLs instead of each carrying a copy. Everything in its `bin` folder is kept except ffplay.
- Checksum files come in two forms: `<hash>  <name>` lines (yt-dlp, FFmpeg-Builds) and PowerShell's `Hash : <HASH>` (Deno's `.sha256sum`). `checksum.rs` reads both.
- An install downloads to `tools\.download-<tool>\`, checks the SHA-256, unpacks to `tools\.new-<tool>\`, then swaps that folder in for `tools\<tool>\` (the old one moved aside, deleted after, put back on failure). Each tool has its own working folders, since the setup installs all three at once. Afterwards the tool is run (`--version`) to catch an antivirus quarantine.
- GitHub allows 60 API requests an hour per network without signing in. The latest release of each tool is cached for 10 minutes, so the setup's sizes and downloads cost one request per tool.
- yt-dlp updates itself with `--update-to stable@latest` (or `nightly@latest`). Naming the release, not just the channel, lets it go back from a nightly build to an older stable one, which plain `--update-to stable` refuses as a downgrade. It renames itself to `yt-dlp.exe.old` while updating and deletes that at its next update.
- ffmpeg, Deno and gallery-dl are compared by the SHA-256 of the release file they came from, stored in `settings.json`. FFmpeg-Builds rebuilds daily under the rolling tag `latest`, so its releases are labelled by date. A copy adopted from `tools\` at setup has no stored checksum, so its first check always offers an update.
- Progress reaches the UI as `tool-progress` events (`ToolProgress`); every install or update ends with one whose stage is `null`. `tools-changed` tells the UI a tool changed on its own (the startup update of yt-dlp).
- A tool's errors reach the UI as `ToolError`, a tagged union; `errors.ts` turns each kind into a sentence from `strings.ts`, with the technical `detail` underneath. `PreviewError` and `HistoryError` work the same way.

### Metadata and Preview

- `metadata::normalize_link` accepts only http and https links with a host (adding `https://` when there's no scheme), so pasted text, a search (`ytsearch:`) or a file path never reaches yt-dlp. The link is also passed after `--`, so nothing in it can be read as an option.
- yt-dlp runs as `--ignore-config --no-playlist --flat-playlist --dump-single-json --encoding utf-8`, with `--js-runtimes deno:<path>` when Deno is set up (`--no-js-runtimes` otherwise, so a Deno on PATH can't hide that it's missing) and `--ffmpeg-location`. `--flat-playlist` makes a playlist or channel answer at once instead of reading each video; `--encoding utf-8` keeps its messages from being mangled by the Windows code page. The Deno path must be a Windows path: yt-dlp silently ignores a `/d/…` one.
- The site is yt-dlp's `extractor_key` in lowercase, as yt-dlp's archive writes it (`youtube`, `soundcloud`, `archiveorg`), and with the video ID it's what the duplicate check matches on. A format counts as video when it has a height and isn't `vcodec: none`, since some sites (archive.org) give no codec.
- yt-dlp reports a failure as its last `ERROR:` line; `classify_failure` sorts it into a `PreviewError` by phrases in it. Upcoming premieres are errors too ("This live event will begin in…"), not a field of the answer. When a site's message changes, add the new phrase and a test.
- **Two tools read links.** `sites::prefers_images` sends image sites (Instagram, X, Bluesky, Pixiv, Tumblr, boorus…) to gallery-dl first and everything else to yt-dlp; `preview::read_link` then falls back to the other tool when the first answers "unsupported" or yt-dlp finds no video (`PreviewError::NoVideo`), or when gallery-dl fails to read a site it knows. A missing sign-in or an unavailable post isn't retried. Without gallery-dl, a photo post is `ImagesNotSetUp`, which the UI offers to fix. The user is never told which tool read a link (the user's choice: tools are internals), so preview errors don't name yt-dlp.
- `gallery::fetch` runs `gallery-dl --config-ignore --dump-json -- <link>`. Its answer is a list of messages: `[2, post]`, `[3, url, file]` per file, `[6, url, …]` for a link elsewhere (a profile's posts, refused as `Playlist`), and `[-1, {error, message}]` for a failure, which still exits 0. Only an unsupported link exits non-zero (64). Signed out, Instagram redirects to its login page and X refuses media timelines, so both need cookies even for public posts.
- A post becomes a `VideoInfo` with `post: Some(PostContents)`. Its key is gallery-dl's category and the post's ID (`post_shortcode` on Instagram, `tweet_id` on X), the same as yt-dlp's archive gives for those sites, so a reel downloaded with either tool is one history entry.
- Pixiv needs a gallery-dl OAuth refresh token (`gallery-dl oauth:pixiv`), not browser cookies, so it fails with a sign-in error for now.
- gallery-dl's Windows build bundles yt-dlp, for the `ytdl:` URLs some extractors (Instagram's DASH videos) use.
- `PreviewService` runs one fetch at a time: starting one cancels the one before, and the UI ignores an answer that arrives after a newer request (`usePreview`).
- `dragDropEnabled` is `false` in `tauri.conf.json`: with Tauri's own drop handling on, WebView2 never gives the page a dropped link.

### File Hosts

- MEGA, MediaFire, Google Drive and Dropbox are read and downloaded by Tsundoku itself (`core::hosts`, `downloads::file_runner`), with no tool, through `reqwest`. `hosts::Host::of` picks them by domain before yt-dlp or gallery-dl is asked, in `PreviewService` and in `ToolRunner` (a job with `files` set). Like the tools, the host stays out of the UI's words, except as the site's name.
- A host's reader turns a link into a `Share`: the file or folder's ID and name, and its files (`RemoteFile`: path inside the download's folder, size, `FileSource`). The preview sees it as a `VideoInfo` with `files: Some(FileContents)` (count and bytes, migration 4: `videos.file_count`, `file_bytes`). The download reads the link again, since download addresses expire, and asks each file's address just before fetching it.
- **MEGA**: the key is the part of the link after `#`, never logged. The API is `POST https://g.api.mega.co.nz/cs?id=<n>[&n=<folder>]` with a JSON list of commands: `{"a":"g","p":<file>}` (or `"n"` inside a folder) for a file's size, attributes and address (`"g"`, missing once the transfer quota is used up), `{"a":"f","c":1,"ca":1,"r":1}` for a folder's nodes. A file's 32-byte key XORs into the AES-128 key; bytes 16–24 are the counter's nonce and 24–32 the meta-MAC. Contents are AES-128-CTR (seekable, so a part file resumes), names AES-CBC with a zero IV (`MEGA{json}`), folder nodes' keys AES-ECB under the folder key. A node's `k` can hold several `handle:key` pairs separated by `/`, and the link's key opens only the one under the shared folder's own node (the folder whose parent isn't listed, `share_root`): that one is tried first, then the rest, and a node none of them opens is left out with what's inside it. The check is MEGA's chunked CBC-MAC (chunks of 128 KiB growing by 128 KiB to 1 MiB), folded to 8 bytes. Error -3 (busy) is retried with backoff, then is a network error like -18; -2/-9 (missing), -11 (access refused) and -16 (taken down) are Unavailable; -4/-6/-17 are LimitReached. Test vectors in `hosts/mega/tests.rs` come from async-mega-py (Apache-2.0); GPL code (megatools, gallery-dl) was read for the protocol only.
- **MediaFire**: `file/get_info.php`, `folder/get_info.php` and `folder/get_content.php` (API 1.4, `response_format=json`, files and folders separately, 1000 a chunk) list a share with sizes and SHA-256s. The address is the file page's Download button (`a#downloadButton`'s `href`, or its base64 `data-scrambled-url`); a page that answers with the file itself is used as it is. That address (`download<n>.mediafire.com/<token>/<key>/<name>`) is also taken as a link, since userscripts and download managers' add-ons copy it: `parse_link` keeps its key and drops the token, which runs out.
- **Google Drive**: a file downloads from `https://drive.usercontent.google.com/download?id=ID&export=download&confirm=t` (plus `&resourcekey=KEY` when the link has one): `confirm=t` skips the virus scan warning on files over 100 MB, with no cookie or form. `hosts::probe` asks for `Range: bytes=0-0`, for the name (Content-Disposition, `filename*` first), size (Content-Range) and date (Last-Modified). An empty file has no first byte: Drive answers 416 without a size, so a 416 is asked again with HEAD, whose 200 attachment gives Content-Length 0 (a Google Doc answers 500 there). A folder is read from `https://drive.google.com/embeddedfolderview?id=ID`, plain HTML: its name is the page title, and each item is a `flip-entry` (`id="entry-ID"`) whose link is a subfolder (`/drive/folders/ID`), a file (`/file/d/ID/view`) or a Google Doc, Sheet or Slides on docs.google.com, which is left out. It has no sizes, so each file is probed, 8 at a time; unlike the `_DRIVE_ivd` data on the folder's own page, it isn't capped at 50 entries. A redirect to accounts.google.com means the item isn't public, and `uc-error-subcaption` "Too many users have viewed or downloaded this file recently" is LimitReached.
- **Dropbox**: a file downloads from its link with `dl=1`, which redirects to `*.dl.dropboxusercontent.com` (Range works), probed the same way. `/scl/` links need their `rlkey` (LinkIncomplete without it); old `/s/` and `/sh/` links don't, and an `/sh/` folder redirects to its `/scl/fo/` form. A folder is listed by the web page's own call, `POST https://www.dropbox.com/list_shared_link_folder_entries` with the form fields `is_xhr=true`, `t`, `link_key`, `secure_hash`, `link_type=c`, `sub_path` (no leading "/"), `rlkey`, and `voucher` (the last answer's `next_request_voucher`) while `has_more_entries`. `t` only has to match a `t` cookie, so any value works. Entries have `filename`, `is_dir`, `bytes` and `href`: a subfolder is listed with its own hash (the second segment of its `href`) and its path, and a file downloads from its `href` with `dl=1`. Errors are pages with status 200, told apart by their title ("Error", "Invalid Link", "No Access", "Log in to Dropbox").
- `file_runner` saves each file to `<temp folder>\<n>.part`, resuming with a `Range` request when the host allows it (206), decrypting MEGA's on the way, then checks it (MAC or SHA-256; Google Drive and Dropbox give only the size), deleting a damaged one (`DownloadError::Damaged`), and moves it to its place with a free name (`Name (2).ext`). A file already at its place with the same size is skipped. Progress is one meter for the whole share, paced to the speed limit. For Google Drive and Dropbox, an answer without `Content-Disposition: attachment` is a page about an error (`Host::page_error`), never written into the part file.

### History

- `tsundoku.db` is SQLite (`rusqlite`, bundled), in WAL mode with foreign keys on, shared by the history and the queue through `database.rs`. Migrations are SQL strings there, applied in order and counted in `PRAGMA user_version`; never change a released one, add one. A database from a newer version is refused rather than read.
- `videos` holds one row per site and ID (with `post_images` and `post_videos` for a post); `downloads` one row per finished download, removed with its video (`ON DELETE CASCADE`); `download_files` every file of a download that made several (a post), removed with its download. A video's download has no `download_files` rows: its `file_path` is the file. Times are seconds since 1970.
- `archive.txt` is rewritten whole (atomically) after every change and when the history opens, in the order videos were first downloaded.
- The UI names a download by its ID to open it or show it in its folder, never by a path, so it can only open files the history recorded.

### History View

- The history view is a list of cards, not a table: the window's minimum width (760 px) can't fit eight columns and a readable title. Sorting is a select with a direction button; it covers every column `HistorySort` has.
- Its results refetch whenever the queue changes (a download finishing adds to the history) and after Forget.
- Download Again in the history puts the video's link in the add bar and opens its preview (`AppActionsContext.showLink`), so the preset is picked and the duplicate warning shown as for any link.

### Presets and Downloads

- [Download Pipeline](./DOCUMENTATION/Docs/Download%20Pipeline.md) covers the queue's states, yt-dlp's arguments, the progress lines, temporary folders and logs.
- Presets live in `settings.json` (`presets.list`, `presets.defaultId`); the four built-ins have fixed IDs and can be reset, others are `custom-<n>`. `Preset::to_args` gives a preset's yt-dlp arguments, and both the editor and the queue use it.
- Extra arguments are split on spaces with double quotes grouping, backslashes left alone for Windows paths. Options that would break progress, paths, the history or the single-video rule are refused, abbreviations included, since yt-dlp accepts them (`--outp` for `--output`); `--progress` is allowed though it begins `--progress-template`.
- A queue item stores a copy of its preset and its resolved folder, so editing a preset or the download folder later doesn't change it.
- **Where a download goes**: `rules::destination`, through `DownloadQueue::destination`, which both adding and the preview card (`download_destination`) use. The first rule that's on and whose conditions all match gives the folder; else the preset's own folder (`Preset::own_folder`); else the download folder, `DownloadSettings::resolved_folder`: the chosen folder or `settings::default_download_folder` (`Downloads\Tsundoku`). `PresetsOverview.default_folder` carries the download folder to the preset editor, so Settings refetches the presets and destinations after changing it.
- **Folder rules** live in `settings.json` (`rules.list`), in order. Conditions compare text ignoring case and the spaces around the value, against every name the download's value goes by: a site matches its extractor key (`twitter`), its domain (`x.com`) and its `SIGN_IN_SITES` name (`X`); a preset its ID and its name. A missing uploader never equals or contains anything. `{site}` (the sign-in name, else the file host's name, else the extractor key) and `{uploader}` are filled in any case, each made safe as one folder's name (`safe_folder_name`); other braces stay. A folder that isn't absolute is joined to the download folder. The catch-all (`catch-all`, no conditions, `{site}` to start with) is always last and comes after a preset's own folder: `rules::destination` takes the first matching rule other than it, then `Preset::own_folder`, then the catch-all when it's on, then the download folder. `rules::with_catch_all_last`, applied when settings are read and in `RuleManager::save`, moves it to the end, drops any conditions, turns the posts rule of 0.1.11 to 0.1.29 (`posts`, "kind is post → {site}") into it, keeping its folder and whether it's on, and puts it back turned off if it's missing, so it can't be deleted; the Rules view adds new rules above it, doesn't offer to move or delete it, and its editor has no conditions. `Settings::from_json` turns a saved `downloads.postsFolder` (0.1.8 to 0.1.10) into a "kind is post" rule (`rules::posts_folder_rule`) above the catch-all when the file has no `rules` yet. `RuleManager::save` replaces the whole list, trimmed and checked, and gives new rules (an empty ID) `rule-<n>`.
- **Grouping and sorting** the Pending and Queue views (`settings.lists`, `ListArrangements`: `list_arrangements` and `save_list_arrangements`): each view keeps a `ListArrangement` (`group`: none, destination, site or status; `sort`: added, title, uploader or site; `descending`). The UI does the work: `arrange.ts` sorts (missing values last, ties by ID) and groups (`GroupPlace`: rank, then label), `components/ArrangedList.tsx` has the toolbar's controls and the grouped list, and `useListArrangement` applies a change at once and saves it, undoing it if saving fails. Pending groups by folder through `useDownloadDestinations`, which shares its answers with the rows' destination lines. `Settings.lists` is read with `default_if_unreadable`, so a choice from a newer version only resets the arrangements instead of setting `settings.json` aside.
- **Pending links** (`core::pending`, the Pending view): text pasted or dropped with several links in it (`pending::links_in`, through `links_in_text`) goes to `PendingLinks` instead of the preview card. They live in `tsundoku.db` (`pending_links`, migration 5), the video as JSON once read. One thread reads them one at a time through `LinkReader` (`preview::ToolReader`, the preview card's own reading without its one-at-a-time cancelling; tests use a fake), oldest first, skipping links on a paced site while the pause after the last one runs (`downloads.postPause`). The duplicate warning and "in the queue" are worked out each time the list is read, so they follow the history; the UI refetches the list on `queue-changed` too. `start` queues a read link with its own preset or the one given (falling back to the default if it was deleted), or marks a link not read yet `start_when_read`, which queues it once read unless the history has it. A second link to a video already here is dropped once read. `pending-changed` carries every link.
- **Clipboard watcher** (`pending::watcher`, Settings → Adding Links: `settings.adding`, `adding_options` and `save_adding_options`): a thread looks at the clipboard's change count every 500 ms (`Clipboard`, on Windows `clipboard::SystemClipboard`: `GetClipboardSequenceNumber`), and reads the text only when it changed while the watcher is on, so what was copied before turning it on is skipped. `SystemClipboard::text` refuses copies owned by Tsundoku's process or its children (WebView2 copies from its own process, found through ToolHelp) and copies carrying `ExcludeClipboardContentFromMonitorProcessing` or `Clipboard Viewer Ignore` (password managers). `watcher::copied_links` takes a copy only when every word is an http(s) link, minus direct file links (`FILE_ENDINGS`, never a file host's). `PendingLinks::catch` adds them with `caught` set (migration 6), skipping links the queue or the history has by the exact address (`has_link`). A caught link is read with yt-dlp's generic extractor off (`LinkReader::read`'s `any_page`, `--ies default,-generic`, which turns down unknown sites offline as "No suitable extractor"). Once read it leaves quietly when there's nothing to download (`nothing_to_download`: unsupported, no video, a playlist, an invalid link, or images without gallery-dl on a site not about images; a file host's link its `parse_link` doesn't take is `LinkNotRecognized`, from `Host::link_not_recognized`, not `UnsupportedSite`, so it stays to say so) or the queue or history has its video; with `download_right_away` the rest go through `start_once_read`. The UI hides caught links until read (`shownPendingLinks`) and counts them as being checked.
- `DownloadQueue` owns its items and runs each download on a thread of its own; `QueueListener` passes changes and progress to the app crate, which sends them as events. The runner is a trait (`JobRunner`), so tests swap yt-dlp for `FakeRunner`.
- **The whole queue**: `stop_all` (Pause All), `resume_all` and `retry_failed` do `stop`, `resume` and `retry` for every item in the state each acts on (`requeue_all` and `put_back_in_line` are shared with the single-item ones). `download_next` moves a waiting item to the front of `items` and saves it in `queue_items.position` (migration 7: 0 when added, one less than the lowest when moved), which `QueueStore::load` orders by, then ID. The tray's Pause All Downloads follows `WholeQueueAction::for_items`: pause while anything runs or waits, else resume while anything is stopped.
- `DownloadSettings` (`settings.json` → `downloads`) is also what the UI edits: the download folder, downloads at once (1–5), the speed limit (checked and written as yt-dlp takes it, such as "900K"), the cookies browser and the pause between a paced site's files (`sites::paces_downloads`, Instagram; `PauseRange`, at most 600 s). The cookies browser applies to previews too, since a video that needs a signed-in account can't be previewed without it.
- `browsers::cookies_for` turns the cookies choice into the `--cookies-from-browser` value for one link, resolved when a preview or a download starts: `BROWSER:PROFILE_FOLDER`, with Firefox's forks as `firefox`. Profiles come from `profiles.ini`/`installs.ini` (Firefox family, under `%APPDATA%`) and `Local State` (Chromium, under `%LOCALAPPDATA%`). The pick reads only cookie hosts, names and last-use times, from a copy of the database made with its `-wal` and `-shm` files (the latest sign-ins live in the log). A running Chromium browser's database can't be copied, so its profiles are skipped. The sign-in cookie of each site is in `sites::SIGN_IN_SITES`. Ported from RJ Library (`Voice Works Library\rj-library\backend\services\external_import`).
- The UI decides what closing the window does (`onCloseRequested` in `queueEvents.ts`, which needs `core:window:allow-destroy` and `core:window:allow-hide`): with `settings.background.keepInTray` it hides the window; otherwise it asks first while downloads run. A JS close listener makes Tauri prevent the close and leave it to the UI, so the app crate doesn't handle `CloseRequested` itself. Windows' dialogs are used for confirmations (`dialog:allow-ask`).
- **Running in the background** (`src-tauri/src/background.rs`, Settings → Running in the Background: `settings.background`, `background_options` and `save_background_options`): the tray icon (Tauri's `tray-icon` feature) exists while `keep_in_tray` is on; its menu's changing items (`TrayMenu`) follow `PendingListener::changed` (Start All Pending's count, `pending::starts_with_all`) and `options_changed` (Watch Clipboard's tick, also sent to the UI as `adding-options-changed`), and the queue's `changed` (Pause All Downloads, `background::queue_changed`). Quit asks through the dialog plugin while downloads run. Start with Windows is `tauri-plugin-autostart`, applied when the setting is saved; Windows starts the app with `--in-tray`, and with the tray on the window then stays hidden (`AppInfo.started_in_tray`, which both the UI and the fallback in `lib.rs` check). Development builds register as "Tsundoku (Development)", apart from the installed app. The clipboard shortcut (`AddingSettings.clipboard_shortcut`, `tauri-plugin-global-shortcut`) is registered at startup and swapped in `save_adding_options` before saving, which fails with `DownloadError::ShortcutTaken` when Windows won't give the keys; pressing it reads the clipboard off the main thread (`clipboard::copied_text`, any owner) and adds its links with `PendingLinks::add_sent`, as if pasted but started once read with Download Right Away. Pages sent from a browser are `tsundoku://add?url=…` links (`pending::SEND_SCHEME`, `pending::links_in_sent_link`), which the Settings bookmark (`SEND_PAGE_BOOKMARK` in `sendPage.ts`, a `javascript:` bookmark copied with `copyText`) opens: `tauri-plugin-deep-link` (scheme in `tauri.conf.json`, so the installer registers it; `register_all` at each start too, pointing it at the build that ran last) reads it from a launch's only argument, and the single-instance plugin's `deep-link` feature hands a second launch's link to the running app, whose callback then leaves the window where it is (`background::is_sent_link`). They go through `add_sent` with a notification too; a launch for a sent page with the tray on starts hidden. Notifications (`tauri-plugin-notification`, from Rust only) go out when `AddingSettings.notify` is on and the window isn't visible, focused and unminimized: `PendingListener::copied_link_read` for each caught link that stays, the shortcut, sent pages, and the tray's Start All Pending. Clicking one focuses the window (`on_action`). The tray's and notifications' texts are in `background.rs`'s `text` module, since they show outside the UI.
